# 告别循环修复：AI 编码的防腐化工程闭环

## 一句话结论

**AI 编码项目的失败大多是工程问题，不是提示词问题。** 症状是"越做越难、改一处坏三处"（腐化），根因是**只给了 AI 一个愿望，没给它一个计划**；解法是把资深工程师的纪律（先规划、显式决策、状态外置、证明能跑、调查式调试）做成贯穿始终的闭环。

## 一、问题：腐化（decay）的三个症状

几乎所有用 AI 从零搭应用的人都会遇到同一组症状，而且每个新功能都在加重它：

1. **不复用**：AI 不去读已有代码，而是新写一个组件、一个新函数，同一份逻辑第三次重复实现。
2. **不积累**：每个功能都让下一个更难做；项目没有把已有工作凝聚起来的东西。
3. **互相破坏**：新功能时不时干掉一个原本正常的旧功能；代码变乱、变慢。

症状之外还有两个更隐蔽的失败：

- **漏做 + 加戏**：AI 漏掉你真正要的，还顺手加了从未要求的功能——修复成本随即变成新一轮提示的开始。
- **原地震荡**：几轮提示之后，你已经忘了最初要构建什么，只能反复解释、反复修复，看着时间和 token 流逝，只为回到"你本以为已经有的状态"。

关键判断：这一类问题**不是靠更好的提示词解决的**。提示词只能优化单次输出，无法提供项目层面的约束。

## 二、根因："你给了它一个愿望，而不是一个计划"

螺旋、漏功能、错误猜测、原地打转，几乎都能追溯到一个源头：**在输入任何内容之前，没有给 AI 一个计划**。

而这个问题软件工程几十年前就解决了，只是当时不是为了 AI：没有哪个严肃团队会先打开编辑器。他们先计划——**要构建什么？第一版包含什么、明确排除什么、按什么顺序？** 需求先于代码，理由很枯燥：**改计划里的一行是免费的，改一个已经扩散到整个代码库的决策等于重写。**

用 AI 构建时，这一步被悄悄跳过了，直接进入了构建环节。恢复它的代价很低，跳过它的代价会随功能数指数增长。

## 三、闭环的五段（这是全文的骨架）

顺序是固定的：**规划 → 设计 → 状态 → 验证 → 调试**。下面每段的"可迁移规则"才是能直接搬到自己工作流里的部分。

### 3.1 规划：先决定构建什么，再碰技术

- **规划阶段不碰技术**。技术栈、数据库、框架是独立的下游决策——把它们混进规划，会让计划在换工具的那天作废。
- 规划要产出的是一份**有序计划**：为谁做、第一版包含什么、什么可以等、谁依赖谁，以及构建顺序（先打穿一条端到端薄切片，还是先发布最小可用版，还是一次做全）。
- 让规划者**反问你**（采访式提问），而不是替你猜。"由你制定、而非 AI 聪明猜测出来的计划"是唯一能对抗后续所有漂移的锚。

### 3.2 设计：把隐性决策摊到桌面上

每个功能内部都藏着**你从未明确指定的决策**：数据怎么存、失败时怎么办、列表要不要分页、用哪个供应商。默认情况下 AI 不会停下来问，它会选"能让程序跑起来"的那个方案，然后把你的选择埋进代码——你继承了这些决策，也继承了随之而来的问题。

可迁移规则：

- 设计阶段必须对**每个真实决策列出**：选项、推荐方案、**诚实的替代方案及其落选的真实原因**。全部写下来，可被否决，而不是埋在代码里。
- 默认值应该是"无聊但可靠"的那一档（先单体、默认关系型数据库、每个列表分页、每个公共端点限流、密钥永不出现在代码里），**除非有具体理由升级复杂度**——先问"这真的需要复杂化吗"。
- **承重检查（机械执行，本文最有价值的一条）**：对功能必须显示或计算的**每一个值**（总数、日期、状态……），都必须指明它的**来源**。**任何没有真实来源的值，就是一个无人做出的决策**——必须在设计阶段抓住它，而不是让 AI 在构建中途凭空捏造。
- 这条检查必须**机械地做**，不能靠"感觉在捏造"。原因很实在：**AI 会说服自己"这只是接线工作"，然后直接跳过。** 所以做法是枚举值 → 对照计划说来源 → 无来源即停机，由人回去做决定。
- 当人被强推着往前走（覆盖检查强行构建）时，**假设要被写进文件、并标记在该功能上**，直到它被正式决定。抄近路可以，但近路必须可见——存在文件里，而不是消失在聊天记录中。

### 3.3 状态外置：项目知识存在文件里，不存在聊天里

每个 agent 都跑在一个上下文文件上（`AGENTS.md` / `CLAUDE.md` / 各工具自己的叫法）。它告诉 agent 项目实际如何运作：技术栈、命令、规范。没有它，每个新会话都从盲目猜测开始，而**每次猜的都不一样**——代码库会悄悄漂移成三种不同风格。

可迁移规则：

- **上下文文件必须写自真实项目，而不是写自"AI 以为你的项目应该长什么样"**：读真实结构、真实技术栈、已做出的决策，然后据此生成。
- **按结构分片**：单体给一份干净的根文件；monorepo 把上下文文件放在正确位置；**通用规则放一处，局部规则放自己模块旁边**——避免一个巨大文件让每次会话都塞满它不需要的规则。
- **永不覆盖人写的内容**：只填空缺；文档与代码不符时**标记冲突让人决定**，不强行覆盖。这条是它在真实团队仓库里可用的前提。
- **持续同步**：文件要随仓库实际状态协调，这样第三个月读到的上下文仍然描述着实际拥有的应用。
- 收益是复利性的：项目知识不再随关闭的聊天消失，新搭档、新队友、完全不同的 AI 工具只要读文件就能接续，**不用再向 AI 重新解释项目**。

### 3.4 验证：证明它真的能跑，"能用"不是答案

AI 会在这里做最后一次欺骗：报告完成、说搞定了，但按钮点了没反应、边界情况崩溃、或者计划要求的功能根本没建出来。

**最危险的陷阱是测试通过率**：绿灯只证明 AI 想到要测的那部分代码，它**从不证明功能真的存在、界面真的建了**。

可迁移规则（四个动作，故意分开）：

| 动作 | 做什么 | 为什么必须独立 |
|:---|:---|:---|
| **运行真实应用** | 驱动实际功能、点击流程、访问端点、观察结果，对照计划逐项检查"要求的东西都在吗" | 区分"测试通过"与"我亲眼看着它工作" |
| **写测试套件** | 针对调用者实际依赖什么、什么会真正破坏功能 | 保护这个功能在六个月后不被附近改动打破 |
| **换模型审查** | 用**不同于写代码的模型**读代码、取差异、评估问题 | 模型审查自己的工作带着自己的盲点 |
| **写文档** | 基于**实际 diff** 写 PR 描述和变更日志，而不是基于"AI 记忆中它以为自己改了什么" | 记录事实而非记忆 |

运行几项**取决于风险**：简单原型只需自检，支付系统四项全跑。**把投入与风险匹配，而不是把流程当仪式。**

### 3.5 调试：调查，而不是模式匹配

出问题时的典型崩坏：让 AI 修，它开始乱改；改一处还是坏的，又改三处还是坏的；20 分钟后你有了五处随机编辑、原始 bug 加两个全新 bug。**这是最纯粹的腐化——试图修复一个问题，制造出三个新问题。**

可迁移的调试纪律（顺序不可换）：

1. **可靠复现**：一个无法按需重现的 bug，就是你无法证明被修好的 bug。
2. **缩小到最小失败点**。
3. **只形成一个根因理论，并且在碰任何别的东西之前只测这一个点**。错了就丢弃那个改动并从中学习——**不留无用编辑**。
4. **一次只做一件事**，且每次有意义的动作。
5. **修原因不修症状**：不是前置一个空值让错误消失，而是找出那个值最初为什么是空的。
6. **写一个"没修复就失败、修复了就通过"的测试**，让这个 bug 永远不会悄悄回来；并**搜索代码里其他地方隐藏的同类错误**。
7. **如果发现根因不是编码错误、而是一个糟糕的决策**——说清楚，**回去重新设计**，而不是用补丁掩盖错误的决策。

一句话区分：**对破碎症状做出反应的 AI，与调查原因的 AI，是两种完全不同的东西。**

## 四、遗留代码库是一等场景，不是例外

大多数教程（包括原视频自己的）都基于全新项目：干净的起点、没有需要对抗的东西、容易教学——但这不是你典型的工作现场。

真实工作面对的是别人写的、存在多年的代码库：没有文档，或者文档早已过时；有一些约定俗成的规则需要**逆向工程**才知道；而且有一半时间它根本不在你看过的教程所用的技术栈里。

关键判断：**问题不是"AI 能不能读懂它"（当然能），而是"整套工程流程能不能跑在你继承的这个烂摊子上"。**

可迁移规则：

- **读取并记录它实际如何工作**，捕获的是**工程上下文而不是某个框架**——所以十五年的 PHP 老库照样能读。
- **规划要纳入"已经建好的东西"**：不假装项目从今天开始，下一个切片要基于既有系统施加的约束（已有数据、已有模式）来设计，而不是在真空里设计。
- 这才是真正的重点：**与现有代码协作而非对抗，是复用而不是重新生成。** 接管真实的、继承来的混乱代码库并在不破坏它的前提下向前推进，是职业生涯里大部分时间实际在做的事——而几乎没有人专门教它。

## 五、反模式速查

| 反模式 | 为什么会发生 | 替代动作 |
|:---|:---|:---|
| 循环修复（改一处坏三处） | 在没找到根因时做模式匹配式修改 | 复现 → 最小点 → 单一假设 → 只测那一个 |
| 以"测试全绿"为完成标准 | 测试只覆盖 AI 想到的部分 | 驱动真实应用、对照计划逐项验证 |
| 让写代码的模型审自己的代码 | 自我盲点 | 换一个模型审查 |
| 让 AI 在代码里默默做决定 | 上下文里没有"决策清单"这个约束 | 值必须有来源；无来源即停机 |
| 用"更好的提示词"解决腐化 | 把工程问题当提示问题 | 恢复计划/设计/状态/验证/调试闭环 |
| 上下文文件写一次就不管 | 代码在变，文档没变 | 按仓库实际状态持续同步，冲突标记而非覆盖 |

## 六、边界与代价

- **不是僵化流程**：小应用不需要与庞大代码库相同的工作流；全新项目与多年项目非常不同。流程要随实际构建的东西、规模、去向调整——**把努力与风险匹配**。
- **判断力不可安装**：跑流程是容易的部分；**知道何时跑哪一个、面临选择时该做什么决定、AI 的建议是否真的适合你的情况、计划偏离时怎么办**——这才是真正的难点，也是工具与能力的分界。
- **AI 无法被 100% 约束**：没有任何提示能捕捉 100% 的问题，但能捕捉几乎所有问题，并在其余问题上提供资深工程师的判断——这与"默默做出所有决定"是完全不同的世界。
