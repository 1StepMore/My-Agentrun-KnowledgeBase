# 巨型代码库的 AI 编码治理：Spec 驱动 + Skill 约束

> 本文不谈某个具体项目、工具或模型。它只回答一个**条件性问题**：当代码库已经大到人无法逐行记忆时，怎么引入 AI 编码，而不让代码质量与 review 成本失控？

---

## 一句话核心观点

大仓库引入 AI 编码，成败不在模型强弱，而在两件事：**你有没有把"什么叫本项目的正确写法"变成机器可加载的约定**；以及**你有没有守住"人只做方向与验收、不下沉到细粒度实现"的位置**。

---

## 适用场景

- 代码库已达**数十万行**量级，模块、接口与调用关系超出单人的记忆容量
- 项目**经手过多人**（多轮交接），风格与约定已经发生漂移
- 想让 AI 承担主要编码量，但**不能接受**质量下滑与 review 成本上升

反向不适用：一次性脚本、原型验证、单人小项目——约定本身的维护成本会高于收益。

---

## 一、先定义问题：AI 编码在大仓库里的两个真实失败点

**1. 风格创造。** AI 天然倾向于"从通用语料里挑一个看起来合理的写法"，而不是"遵循你这个库里已经存在的写法"。同一个问题因此长出三四种实现，腐化由此开始，而 review 成本是跟着实现数量走的。

**2. 人无法逐个把关。** 几十万行里没人记得住每个模块、每个 API 以及它的下游调用关系。所以"让 AI 写完，人再逐行看一遍"这条路径在巨型库里**根本不成立**——人必须换一个位置（见第四节）。

这两点决定了后面的所有手段：要么把约定交给机器（第二、三节），要么把人从细节里抽出来（第四节）。

---

## 二、Spec Driven Development：把约定固化成 skills

这是全部手段的地基：**先把"本项目的正确写法"写成可被 AI 加载的规格**，再谈让 AI 编码。

### 2.1 固化什么——只固化"基础且反复出现"的约定

- 全局异常处理规范
- API 的编写格式与返回结构
- 前后端联调规范（契约、字段、错误码）
- 透传（passthrough）类数据的处理约定
- 前端 UI 规范

**判据：这条约定会不会在几乎每个任务里被反复触发？** 会 → 写进 skill；不会 → 不要写。约定本身也是要维护的资产，写多了会烂。

### 2.2 怎么组织——分层、按角色切

- 按端切：后端写后端的 skill，前端写前端的 skill
- 前端再切两层：**UX 层**（交互、视觉）与**工程化层**（框架选择、样板代码、目录结构）
- 目的：让 AI 在动手前就知道"这个库长什么样"，产出与既有风格一致，而不是另起一套

### 2.3 加 rules——把"不能做什么"也写下来

约定不只有"应该怎么做"，还必须包含**边界**：

- 什么不需要做（避免过度设计、避免顺手重构无关代码）
- 什么绝对不能碰（架构红线、不该改的模块）
- **把架构决策在项目早期固定下来，写进 rules，让 AI 每次编码时默认加载**

> **通用原则：** 先固定架构，再让 AI 编码。约定是**预防腐化**的手段，不是事后补救。

---

## 三、提示词的正确姿势：AI 生成 → 人 review → 再执行

这是本文最反直觉、也最实用的一条。

### 3.1 反面做法：用户视角的需求描述

"给我做一个带追问、最后出报告的智能问答功能"——这是**用户视角**：描述的是**看得见的那个系统**。而真正决定实现质量的底层细节全部被屏蔽了：

| 用户视角说出来的 | 实际决定成败的底层问题 |
|---|---|
| "要有追问" | 模型怎么设计？多轮状态放哪？ |
| "要有报告" | 数据从哪来？渲染在哪一层？ |
| "要能上传材料" | 上传链路、解析、失败重试怎么走？ |
| "要好看" | 交互 UI/UX 怎么组织？ |

用户能看见的功能清单，和工程上要做的决策，几乎是两张不相干的表。

### 3.2 正面做法：三步

1. **先描述大致方向**（你要什么，**不要**描述怎么做）
2. **让 AI 基于你的系统生成提示词**——它读得到你的 skills / rules / 现有代码，所以它能写出贴合本项目的提示词
3. **强制 review 提示词**，确认无误再让它执行任务

### 3.3 为什么要"砍"

模型越强，吐出的工作点越多，一份提示词里出现 10 个以上工作点是常态。人 review 十几项的东西要花很长时间，而且很容易只看个大概就放行。

**建议砍到 4–5 个工作点**：保证人机双方都真正 review 得完，代码量控制在可控范围。

### 3.4 跳过 review 的失败模式

- **传达难掉头**：任务一次铺得太开，中途想改方向时，前面 AI 的工作量已成沉没成本
- **任务过度庞杂**：一个提示词混了多个目标，产出噪音多、边界不清
- **review 变成天方夜谭**：等回头去看 AI 那一大坨改动时，已经无法有效判断对错

> **通用原则：** 提示词的产出方是 AI，批准方必须是人。**提示词是待审文档，不是命令。**

---

## 四、人的定位：往上走，不下沉

把底层细粒度工作交给 AI 之后，人的位置不是"更努力地写代码"，而是**从细节里收出来，往上走**：

- 定义方向、划定边界、验收结果
- 维护约定（skills / rules）本身——这是新的核心工作
- 判断哪些活不该做（避免 AI 过度设计，也避免人去补无意义的细节）

人一旦下沉到很精细的活，就同时失去了两个东西：review 的带宽，和对全局的判断力。

---

## 五、多轮业务 Agent 的记忆与上下文架构（可迁移设计）

以下模式与具体业务无关，任何**多轮对话型业务 Agent**（问答、顾问、客服、流程助手等）都适用。

### 5.1 长期记忆 / 用户画像

- 从对话中提取用户信息（由模型识别），**通过 tools 写入**画像
- 后续其他业务领域再调用 Agent 时，通过 tools **按需解锁**过往画像数据
- 定位：这是系统的**核心资产**，不是附属功能

### 5.2 会话记录

- 每轮 ReAct 过程中与大模型的交互、用户提示，完整落在 session 里
- 与长期记忆分开存：一个是**跨会话**的画像，一个是**单会话**的过程

### 5.3 上下文自治理（关键）

- 上下文窗口是**固定大小**的；超出之后会出现**信息遗漏**与**上下文漂移**
- 方案：**分区压缩**——画像、会话、工具结果、任务态等不同部分用**不同层级的压缩算法**，而不是一刀切摘要
- 目标：把上下文**稳定压在**窗口内，而不是等撑满了再救火

### 5.4 Skill / prompt 的装载：用 Hook，且按领域限定

- 用 Hook 调用 Hook，把系统 prompt 或 skills 加载进上下文
- 业务领域通常数量有限且固定 → **在代码里规定每个领域只能加载对应的 skills**，避免"整个 skills 库全量注入"
- 好处：装载逻辑简单、上下文可控、不会因为 skill 库膨胀而污染每一次调用

> **通用原则：** 记忆分"跨会话的画像"与"单会话的过程"；上下文管理必须是**主动的、分区的、按层压缩的**。

---

## 六、陌生技术栈的边界纪律

- 第一次做的系统、第一次用的框架：网上现成的 skills 可能有点用，但很容易一头雾水
- 即使 AI 给出了看似可用的代码，**自己没搞懂就不该让它上线**——对代码要有敬畏心
- 因此：**不要把注意力放在框架特定的 API 细节上**（例如某种 Web 框架的依赖注入、AOP 这类只在该语言/框架内成立的知识），那类知识 AI 比你熟
- 把注意力放在**可迁移**的部分：架构、约定、验收标准

---

## 七、对读者的可迁移启示

- **约定先于编码**：先写 spec（skills + rules），再让 AI 动手；顺序反了，后面全是返工
- **让 AI 读你的库，而不是你读 AI 的库**：约定的作用是让 AI 主动贴合项目，而不是让人事后逐行对齐
- **提示词是待审文档，不是命令**：说方向 → AI 生成 → 人砍到 4–5 个工作点 → 人批准 → 才执行
- **窗口是固定资源**：上下文要主动分区压缩，等撑满就晚了（参见 [[上下文工程-用磁盘文件替代上下文状态管理]]）
- **记忆分两层**：跨会话的画像 + 单会话的过程，压缩策略分开设计
- **边界纪律**：不懂不上线；把精力放在可迁移的架构与约定上，而不是框架 API 细节
- **通用性自检**：把本文里的框架、模型、业务类型全部替换掉，这套做法**仍然成立**——成立，才说明它值得放进知识库

## 八、不适用的边界

- 小项目 / 一次性脚本 / 原型验证：约定成本 > 收益
- 必须人工全量审查代码的强监管场景：本方法的主要收益（压缩 review 成本）会被抵消
