# 上下文工程：用磁盘文件替代 Agent 上下文状态管理

## 核心洞察

AI Agent 执行长任务时最大的痛点不是模型能力不足，而是**上下文丢失**——历史信息被窗口打满/清空后，agent 不知道自己做过什么、下一步该做什么。

一个朴素但有效的解决方案：**把状态从易失的上下文窗口移到持久的磁盘文件**。这不是新模型或新框架，而是一种工程纪律——用文件系统代替内存。

## 核心哲学：不信任上下文，只信任磁盘

| 概念 | AI 上下文窗口 | 磁盘文件 |
|------|--------------|---------|
| 本质 | 内存（RAM） | 磁盘（Disk） |
| 特性 | 易失、随对话波动 | 持久、可恢复 |

上下文窗口即使从几万涨到百万 token，也解决不了"窗口清空后失忆"的问题。结构化的文件系统是一个被低估的解决方案。

## 三大状态文件

Agent 在执行长任务时维护三份持久化文件：

| 文件 | 用途 |
|------|------|
| `计划.md` | 当前目标、未完成步骤 |
| `发现.md` | 探索过程中得到的事实、教训、约束 |
| `进度.md` | 已完成的步骤、当前状态、检查点 |

即使上下文被清空（`/clear`、会话超时），Agent 从这三份文件中恢复后仍可继续工作，不会失忆。

## 工程机制：文件写入不可跳过

仅靠"建议"Agent 写文件是不够的——需要不可撤销的执行钩子：

1. **初始化钩子**：任务开始时强制创建三份文件的骨架
2. **检查点钩子**：每完成一个步骤后自动追加到进度文件
3. **发现钩子**：遇到新的信息/约束时强制记录到发现文件
4. **重规划钩子**：上下文超过阈值时自动将当前状态全量写入磁盘
5. **完成门**：任务结束前验证三份文件的状态是否一致

## Benchmark 的解读

这个模式的 benchmark 数字（合规通过率 6.7% → 96.7%）具有双面性：

- **正面**：结构的价值远超模型本身的随机性。工程纪律被焊死在流程中时，任务执行稳定性显著提升
- **审慎**：这是一个合规性指标，测量的是 Agent 是否照规矩创建了文件并维护状态，而非模型智商的提升

真正的提升在于：**可复现的工程纪律 > 模型单次推理的随机表现**。

## 更深层的判断：上下文工程是新的状态管理

传统软件开发中，状态管理（数据库、文件系统、缓存）是整个系统可靠性的基础。在 AI Agent 时代：

- **上下文窗口** 正在扮演类似"运行时内存"的角色
- 但多数开发者仍在用"凭感觉塞提示词"的方式来管理
- 结构化工程方案（状态分层、持久化、恢复机制）几乎缺失

将 Agent 的执行状态持久化到磁盘，在效果上等价于为 AI 任务引入了 ACID 级别的可恢复性。这不是一个工具层面的改进，而是一种架构层面的范式切换：如何看待 Agent 的"记忆"。

## 适用范围

- **长任务场景**：AI 编程、多步骤研究、文档批量处理、复杂工作流编排
- **多轮协作场景**：跨会话的长周期项目、团队间 Agent 接力
- **不可中断场景**：耗时较长的自动执行任务

## 与相关模式的对比

| 模式 | 状态管理方式 | 恢复能力 | 工程成本 |
|------|------------|---------|---------|
| 纯提示词 | 依赖上下文窗口 | 低（清空即丢失） | 零 |
| 文件持久化 | 磁盘文件 | 高（可恢复） | 低 |
| 数据库/向量存储 | 外部存储 | 最高 | 中高 |

文件持久化方案在**成本-收益比上最优**：零基础设施投入、与版本控制天然兼容、Agent 可读、人类也可读。这是作者背景的特殊性——Rust 运行时与代理基础设施的工程直觉，而非模型调优的产物。

## 关键教训

- **结构 > 模型**：工程纪律和组织能力对任务成功率的影响，可能大于模型本身能力提升
- **易失 vs 持久**：上下文窗口是内存（易失），磁盘是持久——不要把所有状态押在易失媒介上
- **强制 > 建议**：钩子/门控机制比"提醒"有效得多
- **合规 ≠ 智能**：benchmark 提升说明的是工程纪律的价值，不代表模型变聪明了
