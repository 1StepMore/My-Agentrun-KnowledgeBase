# 本体建模驱动的一体化平台-分层模型体系与运行底座方法论

> **证据等级 E4**：本页提炼自一场技术分享直播（时长 42 分 46 秒，转写 1.42 万字）。讲者是「本体建模规范 v6」的个人作者，**其框架、模型清单与平台演示均为自述，未经独立第三方验证**；文中所有能力演示（需求→本体→应用、源码逆向、指标洞察等）均为讲者现场演示口径。引用时请保留归属。

## 一句话概要

把本体（Ontology）从「建模产物」变成「可运行系统的唯一核心」：用一套**分层的本体模型规范**描述业务，配一套**运行底座**（长上下文管理）与一组**「指导书」**，同一个本体模型就能分别生成 IT 应用、技能（Skill）、MCP 接口、数据分析报告或知识问答。

## 一、出发点：本体建模与传统面向对象建模的分野

传统面向对象分析设计（UML 那套）与本体建模表面相似——都是建类、建属性、建关系、定义行为方法——但**建模的目的不同**：

| 维度 | 传统面向对象分析设计 | 本体建模 |
|---|---|---|
| 建模目的 | 把系统**建设出来**（面向实现） | 产出**可推理、可分析的模型**本身 |
| 规则的位置 | 规则散落为类里的方法，不单独建模 | **规则建模独立成层** |
| 结果形态 | 一簇彼此并行的功能点 | 功能点被规则约束成**相互依赖的网状结构**（类知识图谱） |

**判据**：讲者把「规则建模」单拎出来视为本体建模相对面向对象建模的**核心增量**——它让原本并行的 N 个功能点形成前后依赖与约束关系，从而具备变更影响分析、跨对象推理的能力。这是传统 UML 建模里没有的。

## 二、经典本体论 vs 「静态 + 动态」的本体论

- **经典本体论（OWL / OWL2）**：只有对象—属性—关系，关系里带少量行为与规则、且不全；要定义**跨对象**的约束规则，必须额外增加 SWRL 与 SHACL 这类规则语义文件。
- **Palantir 式本体**：把上述内容归为**静态模型**（对象/属性/关系），再补 **Action 与 Function** 两类定义作为**动态模型**。

**判据**：讲者认为 Palantir 的本体建模「更像传统面向对象分析设计里的 UML 设计内容」，而不是更像斯坦福系的本体编辑器路线（该表述含推断成分，见「待验证点」）。二者的关系是**包含而非并列**：经典本体格式可以看作分层模型体系的一个**可导出子集**。

## 三、分层模型体系：11 个子模型各解决什么问题

讲者给出的子模型清单及各自职责（最狭义的本体只有前三项，其余是为「可运行」而扩展的）：

| 子模型 | 解决什么 | 关键说明 |
|---|---|---|
| 对象模型 | 实体、属性、关系、属性约束 | 与经典 OWL 定义基本对应 |
| 行为模型 | 对象级行为 | 对应 Palantir 的 Action |
| 规则模型 | 跨对象规则、谓词与表达式 | 对应 Palantir 的 Function；**让模型连成网** |
| 事件模型 | 跨对象协同 | 引入事件驱动架构，用**消息解耦**；也为「分析结果异步回写业务系统」预留通道 |
| 场景模型 | 让本体能真正解决业务场景问题 | 规定「哪个场景下如何组装行为规则」；对应 What-If 模拟与假设分析，可固化为 workflow |
| 主体模型 | 岗位、角色、权限 | 对应传统系统的系统管理 |
| 流程模型 | 端到端流程/业务流（类 BPM） | 对应传统系统的工作流引擎 |
| 查询统计报表模型 | 指标定义、口径、计算规则、依赖的表 | 既服务于「从 0 到 1 建系统」，也服务于存量系统的指标分析 |
| 映射模型 | 对象 ↔ 数据库表的映射 | 供大模型把问题转成 SQL 去查库 |
| 接口模型 | 跨业务子域/跨本体的集成协同 | 大企业无法一次建大而全的本体，需按领域拆子域后定义接口 |
| UI 模型 | 界面与菜单结构的提前定义 | 让 AI 编程能自动输出界面 |

**判据**：脱离场景填本体，模型会与真实业务脱节——这是必须单独设「场景模型」的理由。

## 四、落地形态：YAML 为源，经典本体格式为可导出子集

- 整个模型体系的落地形态是**一堆 YAML 文件**：对象、行为、规则各成文件，**行为/规则文件中互相引用**，天然形成连接线；规则里可写谓词与表达式，便于 AI 精确理解业务语义。
- 系统界面上看到的「树状展开」编辑视图，本质只是这批 YAML 的可视化包装。
- **可导出**：任意模型都能导出 OWL、SHACL、SWRL 文件（接回经典本体论生态），但这些格式**无法覆盖**其扩展要素。

## 五、运行底座：为什么必须有长上下文管理

基于规范生成本体模型、基于本体模型生成代码，**都是超长上下文任务**；要把「一次做对」变成可能，底层需要记忆/技艺存储、长上下文管理与**长上下文压缩**能力（即讲者所称的 Harness 层）。

**判据（值得记的一条边界）**：讲者明确说「自建通用 Harness 平台意义不大」——已有厂商把 Harness 开源；他做底座只是**为了支撑上层本体建模**。同时他自陈：**复杂项目在其底座上还不一定能跑得完美，简单项目已全部跑通**。

## 六、组合式扩展：本体模型 + 指导书 = 多输入多输出

核心公式：**本体模型 + 某一领域的「指导书/规范」→ 该领域的产出**。

| 输入 | 组合的指导书 | 产出 |
|---|---|---|
| 业务需求 | 需求探索提示词 + 本体建模规范 | 需求文档 → 本体模型 → **完整应用**（+开发指导书、技术架构、技术底座） |
| 数据库 + 库设计说明 | 数据库设计规范 + 本体建模规范 | 逆向出本体模型 → **指标洞察、场景分析报告** |
| 源代码 | 逆向建模指导书 | 逆向出本体模型 → **变更影响分析**、业务语义库问答 |
| 文档资料库 | 资料库建模指导书 | 基于本体的**知识库/知识图谱与知识问答** |

**同一个本体模型的多种出口**：直接生成 IT 系统、封装为技能（Skill）、发布 MCP server、输出数据分析报告、做知识问答。

**值得迁移的两个设计**：

1. **不让 AI 每次重建基础设施**：任何 IT 系统都有的流程引擎与系统管理不重写，而是先在**既有技术底座**上定义技术架构（语言/微服务/前后端/数据库），再叠加业务功能；流程需求则在既有流程引擎上新建流程。
2. **把分析流程固化为阶段 workflow**：现场演示的场景分析报告被拆成「阶段零初始化 → 阶段一采集与指标计算 → 阶段二异常判定 → 阶段三归因 → 阶段四大模型推理 → 阶段五出报告」，**防止 AI 完全按自己的思路自由发挥**。

## 七、人机分工的关键判据

> **AI 不能自动生成本体模型。** 业务必须由人聊清楚、逐步确认；AI 只是把需求文档**转成**本体模型的 YAML 描述。

演示中的需求探索环节也印证这一点：AI 会基于提示词划分业务域、识别关键业务对象，然后**持续向人提问确认**（业务流程、业务对象、业务规则、岗位角色、权限、数据模型、流程模型逐项梳理），而不是一次生成。

## 八、可迁移性判断（换一个工具/项目还成立吗）

**成立、值得吸收的**：

- 本体建模与面向对象建模的目的差异，以及「规则建模独立成层」带来的网状约束能力
- 11 个子模型的分层清单（作为设计 checklist：对象/行为/规则是核心，事件/场景/主体/流程/映射/接口/报表/UI 是走向可运行系统的补齐项）
- **本体 + 指导书**的组合式扩展模式（一套模型多种出口）
- 三条下游链路：源码逆向 → 变更影响分析；指标洞察 → 场景分析报告；知识萃取 → 知识图谱问答
- 「业务必须由人确认，AI 只做格式转换与推理」的人机分工判据

**不成立、绑定讲者个人实现的**：具体 v6 规范文件、其平台的功能与界面、其底座选型与稳定性表现（自陈复杂项目尚不稳定）、以及具体产品名（Harness 底座、Skills 市场等形态）。
