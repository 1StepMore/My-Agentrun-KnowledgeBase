# Jev 决策模型：决策型 AI 的定位、实测数据与选型边界

## 一句话结论

**Jev 是"决策型模型"，不是"生成型模型"**：它不输出文本、不做推理链，只对"是/否、选哪个、打几分"给出**带概率的结构化答案**。它的价值不在更聪明，而在**把判断从"提示词 + 大模型"迁移到"契约化 + 极低成本"的那一类**；一旦任务需要生成文本、或需要长上下文，它就不适用。

判断口径：**它不是大模型的替代品，而是 `if/else` 里那部分判断的替代品。**

## 二、定位：System 1 型，命名来自两个经典概念

- **System 1**（出自卡尼曼《思考，快与慢》）：面向软件可直接消费的**快速结构化决策**而构建——"快速"指不等推理链，"结构化"指返回数据而非聊天文本。
- **名字由来是杰文斯悖论**：效率提升反而推高总消耗（蒸汽机效率提高 → 煤炭总用量上升）。TypeSafe 预计 AI 决策成本的骤降会让它被用于**过去成本上不划算的大量场景**。
- **训练方式 RLCD**（校准决策强化学习，Reinforcement Learning from Calibration Decisions），由联合发明 ChatGPT 的研究者公开（TypeSafe 博客）。
- 心理模型：**智能 `if/else`**。经典例子——"顾客还差一件就免运费"是纯计算题（别用 Jev）；"这条消息听起来沮丧吗"这类**语义判断**才是它的位置。

### 与生成型模型的对照

| 维度 | 决策型（Jev） | 生成型（GPT/Claude 类） |
|:---|:---|:---|
| 输出 | 概率、选项、分数（JSON 可直用） | 文本 / 推理链 / 代码 |
| 能做什么 | 判断、分类、路由、打分 | 判断 **且** 回复、解释、生成 |
| 能否解释答案 | 不能 | 能 |
| 延迟 | 官方 70–500 ms 端到端 | 秒级起，随输出长度增长 |
| 成本 | 只收输入 token，输出免费 | 输入 + 输出双向计费 |
| 上下文窗口 | **小**（约 64k，实测口径） | 常接近 100 万 |

## 三、接口契约：状态 + 问题 → 结构化答案

**输入**：`状态`（纯文本、JSON 对象或数组）+ 一个或多个`问题`，每个问题带**名字**和**类型**。

**三类问题类型**（这是全部原语）：

| 类型 | 用途 | 返回什么 |
|:---|:---|:---|
| **Noul** | 是/否判断 | `P(是) ∈ [0,1]`。0.95 = 95% 认为是；**接近 0 不是"不确定"，而是相当确定"否"**；0.5 才是无明显倾向。Noul **不单独返回置信度** |
| **Choice** | 从你给的选项里选一个 | 选中项 + **所有选项的概率**。选项由你定义，**必须留"其他"兜底**，否则不符合预设的消息无处可去 |
| **Score** | 按你定义的有序量表打分 | `score` = 各等级概率的**加权平均**（因此可以落在等级之间，如 1.5 / 1.02）+ 各等级概率 + 等级到描述的图例 |

**关键设计细节**：

- **量表等级要写清每级的含义**（如"提出请求但未表达不满 / 表达不满 / 表达强烈愤怒"）——给 Jev 更具体的判据，能明显改善一致性。
- **同一状态上的多个问题合并为一次请求，由 Jev 并行独立评估**。注意副作用：**问题之间互相不可见**，每个问题只能凭你提供的状态成立。这既是并行压缩成本的原因，也是一条硬约束。
- **响应包含**：按问题名对应的答案、模型版本号、token 用量。
- **概率 ≠ 正确**：置信度只是分布，不代表准确。**要用代表性样本自测，自己决定审核阈值**（示例中把"沮丧且高置信"的邮件标记给人工复核，阈值 0.8 是举例如非推荐值）。

## 四、性能与成本：官方口径 vs 独立实测（分层标注）

| 指标 | 来源 | 数据 |
|:---|:---|:---|
| 延迟 | **官方** | 端到端 70–500 ms |
| 相对优势 | **官方宣称（待核）** | 快 20–200 倍、便宜 40–400 倍，输出 token 免费 |
| 价格 | 官方 | 每百万输入 token **4.2 美分**（每十亿 $42），输出免费 → 1 美元约 **4.7 万条**（按每条含问题约 500 输入 token 估算） |
| 单任务对比 | 作者实测（单点） | 某任务 GPT-5.6 Terra ≈ 8.6 s，Jev **114 ms**；同例成本 GPT ≈ 1.4 美分，Jev **不到 1% 美分**（约 1/170） |
| 1000 封邮件 × 7 条规则 | 作者实测 | Jev **70 s / 9 美分**（未并行）；**优化后端并行后 6 s / 9 美分**；对照 GPT-5.6 Luna 5.6 **≈5 分钟 / 62 美分**（约慢 46 倍、贵 12 倍） |
| 1000 封单一分类 | 作者实测 | 4 s / 5 美分（763 是、237 否） |
| 1000 条 YouTube 评论 | 作者实测 | 5 s / 5 美分 |
| 累计用量 | 作者实测 | 约 2 万次请求累计花费 **85 美分** |

**读这张表的正确方式**：官方口径只保证延迟与定价；速度/成本的倍数优势来自作者自测（单机、未校准的横评），**量级可信，具体倍数不可直接引用**。另有一条结构性结论值得记住：**Jev 的吞吐上限很大程度取决于你的后端是否并行**——串行 70 s 的任务，后端并行后 6 s，模型本身没变。

## 五、12 个实测用例：共性全是"分类/判断"，没有一个是"生成"

| 场景 | 任务形态 |
|:---|:---|
| 邮件处理（7 条规则） | 是/否分类（发票收据、品牌合作、钓鱼）+ 类型分类 + 紧急度打分 + 赞助意向打分 |
| YouTube 评论分诊 | 是否值得回复、能否提供选题、情感倾向、问题难度 |
| 社群/论坛帖子 | 问题类型、是否需要帮助、是否需团队回复、流失风险、成员水平、推荐力度 |
| X 信息流标注（Chrome 扩展） | 突发 / 干货 / AI 垃圾三分类，实时逐条判断 |
| 会议转写分析 | 通话类型、是否有决策、是否有行动项、有没有明确的负责人与时间 |
| 视频片段筛选 | 能否单独发布、钩子强度、类型、是否需展示屏幕、有无可引用金句 |
| 合同审核 | 风险类型、条款类型、关注项 |
| 招聘与线索 | 风险信号、线索质量、下一步建议 |
| 想法收集器 | 内容是想法/任务/日记，截止时间、优先级、所属领域 |
| 客服支持 | 情绪、紧急度、待办事项、工单分类 |
| 模拟交易（**作者明示未验证**） | 每秒判断涨/跌并下单 |
| 游戏/浏览器操作 | 只做"下一步该干什么"的决策，执行交给别的模型 |

**共性提炼**：全部是"**大量条目 × 少类判断**"。这决定了它的甜点区——**数据量越大、判断越短、越重复，收益越大**；反过来，条目少、需要理解原因、需要头脑风暴或对话的场景，继续用生成型模型。

一条重要的工程结论：**"Jev 自己不会替你分析。"** 但只要**策略性地设计问题**，就能让数据自己讲故事——不能让 Jev 读完几千份转写后直接告诉你"会议该如何改进"，但可以设置分类与评分，让这些问题**自己聚合出结论**。

## 六、可迁移方法：黄金数据集评估法（本文最值得带走的部分）

引入任何"便宜快但可能不够准"的模型，都应该先做这一步，而不是先接入生产：

1. **准备黄金数据集**：约 **100 个用例 + 正确答案**。
2. **横向跑多个候选**（示例：Jev / Opus / Sonnet）。
3. **三维度对比**：**准确率 × 成本 × 速度**；如果场景看重延迟，速度要单列进评估。
4. **选"准确率—成本平衡最好"的那个**，而不是默认用最强模型——**默认用最强模型，等于永远为不需要的准确率付费**。

补充纪律：**别因为便宜就盲目相信结果**；置信度阈值必须用自己的数据标定，并用代表性样本验证。

## 七、边界与失败场景（硬约束）

1. **不生成文本**：不写回复、不做总结、不生成代码。它能判断信息，但不会替你产出结果。
2. **上下文小**（约 64k，远小于生成型模型的近百万）：大批量任务必须**分批**或按条切分。
3. **不做并行就慢**：串行处理大批量时优势会大幅缩水，后端并行是发挥成本优势的前提。
4. **能精确算出来的就别用它**：算术、日期比较、技术比较、购物车数量——写代码算，更快更准。
5. **需要枚举答案**：只有当答案可以**列成有限选项/量表**时才适用；开放式问题不适用。
6. **置信度不等于正确**：需要自测确定阈值，并设计人工复核兜底。

## 八、选型判断表

| 情形 | 选择 |
|:---|:---|
| 成千上万条数据需要分类/判断/路由，要压低成本 | ✅ 决策型（先做黄金数据集评估） |
| 需要毫秒~亚秒级的实时判断（交互、游戏、实时标注） | ✅ 决策型 |
| 想把"前置过滤/分诊"从昂贵模型上卸下来 | ✅ 决策型做过滤 → 生成型做输出 |
| 需要写回复、总结、提炼主题、深度分析 | ❌ 生成型 |
| 单条或少量条目需要理解原因、头脑风暴、对话 | ❌ 生成型 |
| 答案能精确计算 | ❌ 直接用代码 |

**组合模式（最实用的落地形态）**：决策型模型做**前置过滤与路由**——先把"哪些评论需要回复"挑出来，再把结果交给能真正撰写的生成型模型。这样就不必一开始就用更慢更贵的模型去处理全量数据。

## 九、接入现状与生态（截至 2026-09-22）

- **发布与热度**：2026-09-15 发布，社交平台讨论量已达数千万级浏览。
- **可用通道**：早期体验/后补名单；可通过网关类服务（Bersol 网关〔待核〕、OpenRouter）调用；官方提供 TypeSafe SDK 与 **TypeScript/JavaScript SDK**，并有 Playground 免搭建试用。
- **调用形态**：SDK 中定义 `state`（如一个 `message` 字段）→ 调用 System 1 → 传入问题（命名 + 类型 + 指向 state 字段）→ 取 `answers` 中按问题名的结果与用量信息。
