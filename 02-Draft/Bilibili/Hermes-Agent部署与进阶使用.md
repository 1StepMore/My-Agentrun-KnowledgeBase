# Hermes-Agent部署与进阶使用

部署任何自托管 AI Agent 前，先确认三个基础条件，否则后续排错成本极高。

**操作系统兼容性**。多数 Agent 框架优先支持 Linux 与 macOS，对原生 Windows 不友好。Windows 用户需先安装 WSL2（Windows Subsystem for Linux），在子系统内运行。判断标准：官方文档若明确「不支持 Windows」，则 WSL2 是唯一路径，而非可选项。

**网络环境可达性**。安装脚本通常需要访问 GitHub、npm、pip 等源。若所在网络需代理，务必在安装前配置好代理环境变量，否则会出现两类典型故障：安装中途 443 超时、聊天通道「假连通」（消息发出但收不到回复）。代理配置的关键参数是 IP 与端口，需从系统网络设置中读取，并确保代理软件允许终端流量通过。

**资源下限**。2 核 CPU、4GB 内存（推荐 8GB）、10GB 磁盘是常见基线。低于此配置，安装可能成功但运行时频繁卡顿。

## 一键安装的真相：脚本自动化与手动干预点

现代 Agent 框架普遍提供「一键安装」脚本，形式通常为 `curl ... | bash`。脚本会自动完成：系统架构检测、运行时安装（Python/Node.js 等）、依赖拉取、全局命令注册。但这不意味着全程无人值守，有三个手动干预点：

1. **Shell 配置重载**。安装完成后需 `source ~/.bashrc`（或 `.zshrc`），否则新注册的命令不可用。这是新手最常忽略的步骤。
2. **系统密码输入**。脚本在安装系统级依赖时可能触发 sudo 密码提示，终端输入时不回显，属正常现象。
3. **网络错误重试**。若安装中断于 443 错误，通常是节点问题，切换代理节点后重跑脚本即可，无需清残留。

安装成功的判据不是「脚本跑完」，而是版本命令能正常输出。从执行脚本到验证通过，耗时约 3–10 分钟，取决于网络质量。

## 模型接入策略：成本、授权与版本选择

Agent 框架通常支持 200+ 模型后端，但「支持」不等于「推荐」。接入策略应遵循三条原则：

**优先走聚合通道而非官方直连**。官方旗舰模型 API 价格昂贵，通过第三方聚合服务（如 OpenRouter 类平台）或共享订阅账号，可将成本降低一个数量级。共享账号的典型价格带在每月几元到十几元，但需注意并发限制与供应商可靠性。

**设备授权是共享账号的隐藏门槛**。使用共享订阅时，首次接入可能卡在「设备代码授权」步骤——供应商未在后台开启此开关，用户侧无法自助解决，必须联系卖家开启。这提示了一个通用经验：购买共享服务前，先确认目标平台的设备授权策略。

**版本选择遵循「新而不追」**。交互式配置中会列出可用模型版本，选择最新稳定版即可，不必追求预览版。判断标准：社区讨论热度与官方文档标注的「推荐」标记。

## 多平台接入的通用模式：机器人创建 → Token 授权 → 配对码确认

接入微信、飞书、Telegram 等消息平台，流程高度相似，可抽象为三步：

**第一步：在平台侧创建机器人**。Telegram 通过 BotFather 创建，获取以 `_bot` 结尾的用户名与 Token；飞书在开放平台创建应用；微信走扫码授权。核心动作是获取平台的机器人凭证。

**第二步：在 Agent 侧粘贴凭证并绑定用户**。将 Token 粘贴到终端后，还需指定「谁可以与该机器人对话」——通常是你的平台用户 ID。获取方式：在平台内搜索官方 userinfo 类机器人，自动识别。

**第三步：配对码确认**。部分平台（如微信、飞书）在首次对话时，机器人会返回一条配对指令，需复制回终端执行，才算完成双向绑定。跳过此步会导致「消息能发但无响应」。

**权限配置的推荐默认值**：配对方式选「实名配对」而非「允许所有」；群聊回复选「仅被 @ 时回复」而非「全部回复」。安全边际优先，后续可随时调整。

## 故障排查的优先级排序

多平台接入后最常见的故障是「部分通道无响应」。排查顺序应遵循从底层到上层的原则：

1. **网络层**：代理配置失效是首要嫌疑。重新执行网络配置命令并重启网关，多数「一直在思考/无响应」问题在此解决。
2. **进程层**：某平台通道的进程可能被占用，需结束进程后重启网关。判断方法：重启时若提示「进程被占用」，即为此类问题。
3. **配置层**：检查配对码是否完成、Token 是否过期。

一个实用技巧：终端直接对话测试通过，但某平台无响应，问题几乎必然出在该平台的通道配置而非模型本身。

## 从「聊天机器人」到「知识库」：LLM Wiki 的三层架构

Agent 的高级价值不在于聊天，而在于知识管理。当前主流实践是复刻 Andrej Karpathy 提出的 LLM Wiki 模式——将知识库组织为三层结构：

| 层级 | 内容 | 维护者 | 核心角色 |
|------|------|--------|----------|
| 原始来源层 | 论文、文章、数据文件、会议纪要 | 只读不改 | 事实的唯一源头 |
| Wiki 页面层 | 摘要、实体、概念、综述、交叉引用、索引 | 大模型创建与更新 | Agent 的工作记忆 |
| 协同进化层 | Schema 配置、结构约束 | 人类与模型共同迭代 | 纪律约束机制 |

与[[RAG]]的本质区别：RAG 是无状态检索——每次查询从零开始，知识不积累；LLM Wiki 是有状态学习——增量摄入、持续更新、知识复利增长。判断一个知识库方案是否值得投入，就看它能否实现「越用越懂」而非「每次重来」。

## LLM Wiki 的工作流：摄入 → 编译 → 交叉引用 → 归档

实际使用中，LLM Wiki 遵循四步工作流：

**完整摄入**。将文档（PDF）或论文链接（ArXiv）发送给 Agent，它先完整读取并理解语义，而非分块向量化。此阶段 Agent 会与用户讨论关键要点，确认研究方向。

**知识编译**。摄入完成后，Agent 自动创建/更新摘要页、实体页、概念页，并写入索引文件。此阶段可观察页面数量的增长——例如从 13 页增至 17 页，每篇论文摄入约新增 2–4 个页面。

**交叉引用**。新知识与既有概念建立链接，形成知识网络而非孤立文件。

**查询与归档**。用户提问时，Agent 基于 Wiki 回答，并将有价值的问答归档为新页面。这是数据飞轮的关键闭环——每次使用都在增值。

## 多 Wiki 管理与可视化：Obsidian 作为前端

LLM Wiki 的进阶玩法是「多库并行 + 合并」。可创建多个独立 Wiki（如「微调论文库」「Agent 记忆库」），通过指令无缝切换；当主题重叠时，可指令 Agent 自动合并，合并后索引与交叉引用自动更新。

Wiki 的底层是 Markdown 文件，因此可直接用 [[Obsidian]] 打开查看图谱（Graph View）。这提供了双重价值：人类可读的可视化知识网络，以及 Agent 可维护的结构化数据源。选择知识库方案时，「生成物是否可被通用工具打开」是一个重要判据——锁定在专有格式的方案风险更高。

## 自我进化机制：从隐性反馈到策略微调

「越用越聪明」的实现机制，是 Agent 框架与普通工具的分水岭。典型实现路径：

1. 每次对话结束后，系统收集隐性反馈（用户是否采纳回答、是否追问、是否纠正）
2. 定期用 DPO（直接偏好优化）微调内置的对话策略模型
3. 好的回答模式被强化，差的被抑制

这意味着 Agent 的行为改进不依赖手动调 prompt，而是自动化的策略迭代。评估一个 Agent 框架的进化能力，可问三个问题：反馈如何收集？微调周期多长？用户能否干预微调方向？

## 选型对比：多平台、记忆与进化能力

| 特性 | 成长型 Agent | 通用编排框架 | 工作流平台 |
|------|:---:|:---:|:---:|
| 多平台消息接入 | ✅ 14+ | ❌ | ❌ |
| 持久记忆 | ✅ 三层 | 部分 | 部分 |
| 自我进化 | ✅ | ❌ | ❌ |
| 部署难度 | ⭐ 极易 | ⭐⭐⭐ | ⭐⭐ |

选型判据：若核心需求是「个人助理 + 知识库」，优先考虑成长型 Agent；若需求是「多 Agent 协同完成复杂任务」，则编排框架更合适。不存在普适最优，只有场景匹配。
