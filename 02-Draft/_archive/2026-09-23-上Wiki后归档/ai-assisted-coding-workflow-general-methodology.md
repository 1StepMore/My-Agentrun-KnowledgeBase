# AI 辅助编码工作流：从零构建项目的通用方法论

> 这不是一份工具教程，而是一套**可复用的方法论**。无论你用什么 IDE、什么模型、做什么类型的项目，这些原则都适用。

---

## 核心信条

> **"先想清楚再做，比你让 AI 带着你乱做，结果好得多。"**

这是整条视频的第一句话，也是最核心的一条。AI 编码最大的陷阱不是模型不够强，而是**跳过思考阶段就让 AI 开写**。

---

## 一、项目启动：三段式调研（杜绝"上来就写"）

**很多人跳过这步，后面结果就很差。** 在打开 IDE 之前，先做三件事：

### 1.1 竞品与方案调研
- 有没有同类产品/方案？市面上已经有哪些？
- 它们用什么技术路线？有哪些坑？
- 判断项目的核心难点在哪——不是凭感觉，而是真正想清楚"最难的部分是什么"

### 1.2 技术栈决策
- 基于调研结果，选择合适的技术栈
- 判断做成什么形态（Web 应用？CLI 工具？桌面应用？）
- 确认每个组件为什么选这个，不选那个

### 1.3 工具清单确定
- 列出项目需要的所有外部工具/API/服务
- 对每个工具，**提前阅读其文档**，理解它"能做什么、不能做什么"
- 这让后续的 Prompt 可以更精确：你知道工具的能力边界，就能告诉模型具体怎么做，而不是笼统地让模型"自己想办法"

> **关键原则：** 调研阶段的输出是一份物理文档（架构规划/Markdown 文件），而不是只在脑子里。这份文档会被反复引用。

---

## 二、环境配置：让模型"原生理解"你的工具（最值钱的环节）

AI 编码模型的上下文窗口再大，也不可能在每个 Prompt 里携带完整文档。解决方案是 **Tooling 集成层**：

### 2.1 Agent Skills
- 很多现代工具提供 Agent Skills 包，安装后模型自动知道怎么用这个工具
- 不用 Copy-Paste 文档，不用手动拆解 API

### 2.2 MCP Server（核心模式）
- MCP Server 让模型**直接在工具调用层面**理解和使用外部服务
- 模型可以搜索文档、调用 API、管理资源——就像人类开发者能查文档一样
- 配置一次，后面所有 Prompt 都不需要手动传递工具细节

### 2.3 Project Rules
- 在 IDE 中设定项目级规则（如 Cursor Rules），这些规则会持续注入上下文
- 常见规则：自动 Commit、代码风格、测试要求等
- **好处：** 不用每次重新提醒模型该怎么做

### 2.4 版本管理自动集成
- 配置 GitHub MCP Server 或类似工具，让模型自动创建仓库、自动 Commit
- 降低心理负担——模型做的每一步都可回滚

> **通用原则：** 工具配置工作应该在写第一行业务代码之前完成。这部分投入的时间，会在后续开发中以 10 倍效率回收。

## 三、Prompt 策略：分阶段、讲方法

不要把所有信息塞进一个 Prompt。视频中展示的分段策略：

### 3.1 第一阶段：建立上下文文档
- 向模型描述项目目标、技术栈选择、工具清单
- 让模型生成一份架构/规划文档（Markdown）
- 这份文档成为项目的信息锚点，后续所有会话都可以引用

### 3.2 第二阶段：让模型先提问
- 在初始 Prompt 中明确要求模型**先提出不清楚的问题**
- 逐一轮回答，确保双方对项目理解一致
- 这比"我以为我说清楚了"要可靠得多

### 3.3 第三阶段：分功能、分步骤执行
- 每个 Prompt 聚焦一个功能点
- 先让核心链路跑通，再迭代细节
- 一次只改一件事

### 3.4 Debug Prompt 的特殊写法
- **不要只丢报错信息。** 给出上下文：哪个步骤成功了、哪个步骤失败了、你期望的结果是什么
- **截图 + 标注** 比纯文字描述高效得多——模型可以直接看到 UI 上的问题
- 指出问题位置（"Captions 被播放器遮挡"比"字幕有问题"好 10 倍）

## 四、模型选择策略

**不同阶段用不同模型，而不是一个模型打全场：**

| 阶段 | 推荐模型 | 理由 |
|------|---------|------|
| 从零搭建新项目 | 最新最强模型（如 Claude Sonnet） | 需要最好的理解力和生成质量 |
| 大规模重构/反复改错 | GPT-5 或同级别 | 处理复杂逻辑修改更稳定 |
| UI 调整/小改动 | 速度优先的模型 | 成本低、响应快，不需要最强推理 |

> **通用原则：** 昂贵模型用在刀刃上（架构、复杂逻辑、第一次构建），便宜模型用在重复性调整上。

## 五、Debug 循环：真实的 AI 编码工作流

视频展示的最核心洞察：**AI 编码不是"Prompt → 完美结果"的一次性过程，而是反复迭代的循环。**

### 5.1 观察（最重要的一步）
- 仔细看模型生成的代码做了什么
- 看工具调用日志——这能让你快速判断模型是否跑偏
- 如果模型在调一个不存在的 API，或者用错了工具，你马上就能发现

### 5.2 诊断
- 这个 bug 是逻辑问题、API 调用问题、还是模型理解偏差？
- 截图 + 标注问题位置
- 给出错误信息 + 上下文（"X 成功了，Y 出问题了"）

### 5.3 修正
- 精确描述你要的修改（"不要发整个视频，先用 ImageKit 提取音频再发"）
- 如果模型跑偏了，及时打断，而不是让它继续浪费 token

### 5.4 验证
- 测试修复是否生效
- 如果没生效，回到 5.1

> **通用原则：** 不要当"无脑重试者"——读报错、看代码、理解模型在干什么。你在 AI 编码工作流中的角色不是打字员，而是**架构师 + 质量门控**。

## 六、上下文管理：多人/多地/多会话协作的工程化方案

当项目复杂到需要多个 Agent 或跨会话协作时，需要工程化的上下文管理：

### 6.1 物理文档化
- 架构决定、技术选型、工具配置信息以 Markdown 文件保存在项目中
- 任何新 Agent 启动时都可以引用这些文件

### 6.2 规则机制
- IDE 级别的 Rules（如 Cursor Rules）持续注入工作方式规范
- 不会因为开了新会话就丢失上下文

### 6.3 工具配置可重现
- MCP Server 配置、Agent Skills 安装、API Keys 管理都要可重现
- 换个机器、换个开发者，拉下来就能运行

## 七、从视频中可以习得的元能力

这份方法论提炼到最后，其实是这样几条**元能力**：

1. **信息摄入能力** —— 在让 AI 做事之前，自己先做功课。读文档、看竞品、理解工具
2. **分层思考能力** —— 把事情拆成：调研 → 架构 → 环境 → 编码 → debug → 优化，每层专注一件事
3. **精确表达需求的能力** —— 上下文 + 截图 + 错误信息 + 期望结果 = 高效的 Debug Prompt
4. **打断的能力** —— 当模型跑偏时，及时打断，而不是浪费 token 等它绕回来
5. **工程化习惯** —— 规则、MCP、自动 Commit——这些不是"高级玩法"，是**基础设施**

---

## 八、与"常规开发流程"的根本差异

| 维度 | 传统开发 | AI 辅助开发（本文方法论） |
|------|---------|------------------------|
| 调研阶段 | 自己做 | 让 AI 帮你做（Claude Code 生成幻灯片） |
| 环境配置 | 手动配 SDK/CLI | 通过 MCP Server + Agent Skills 集成 |
| 编码 | 手写 | 以 Prompt 驱动，模型生成 |
| Debug | 自己读代码、查 log | 截图+报错+上下文告知模型，让模型修 |
| 上下文管理 | 项目文档 | 规则文件 + 架构文档 + MCP 配置（可被模型读取） |
| 工具能力传递 | 读文档 + 记 API | MCP Server 让模型"原生理解"工具能力 |

---

## 关键洞察

> **"如果我没有提前配好 MCP Server 和 Agent Skills，没有花时间做规划和调研，后面要多花几倍时间——甚至可能根本做不完。"**

AI 编码工作流的瓶颈从来不是模型能力，而是 **"人怎么组织这个协作过程"**。

- 你花在环境配置上的 1 小时，会在后续开发中省下 10 小时
- 你花在调研和规划上的 2 小时，会避免后面 20 小时的返工
- 你把架构决定写成物理文档的 10 分钟，会让下一次启动新会话时省去 30 分钟的重新说明
