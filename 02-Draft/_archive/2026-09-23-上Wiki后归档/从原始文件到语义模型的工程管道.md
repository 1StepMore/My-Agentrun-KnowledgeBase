# 从原始文件到语义模型的工程管道

## 场景设定

企业数据通常包含三类，每类需要不同的处理路径：

| 数据类型 | 示例 | 特征 |
|---------|------|------|
| 结构化数据 | CSV/DB 表格 | 有固定 schema |
| 半结构化数据 | JSON 嵌套数据 | 有结构但层次复杂 |
| 非结构化数据 | PDF 扫描件、图片 | 无固定结构 |

## 五阶段管道

### 阶段 1：数据连接

核心原则：数据从原系统拉进来时**不做任何预处理**，所有变换在内部完成。这样能从语义层的任意数据点追溯到最原始文件。

拉取方式两种：
- **Snapshot**：每次全量替换
- **Append**：只追加新数据

### 阶段 2：存储

| 存储类型 | 用途 |
|---------|------|
| Dataset | 通用存储容器，每次更新有版本记录（Git for Data） |
| MediaSet | 图片/视频/音频/PDF，可与 AI 提取工作流集成 |

**关键设计**：Media Reference——Dataset 的一列可以指向 MediaSet 里的文件，把结构化和非结构化数据关联起来。

### 阶段 3：管道转换（核心）

三类数据走三条不同路径：

**路径 A：结构化 CSV**
- 自动扫描样本推断类型（时间/数字/文字）
- 可视化拖拽做过滤、去重

**路径 B：半结构化 JSON**
- 核心操作：把嵌套数组炸开摊平成独立行
- JSON → 两张关联表，用关联 ID 连接

**路径 C：非结构化 PDF**
五步走：
1. 文件 → 媒体存储
2. OCR + 多模态视觉模型 → Markdown
3. 从 Markdown 解析业务字段
4. **校验与复核**：格式检查 + 置信度过滤 + 人工抽样核查（最容易被跳过的关键步骤）
5. 输出结构化表，每行保留指向原始文件的列

### 阶段 4：语义映射

| 数据概念 | 语义层概念 |
|---------|-------------|
| 干净的表 | 对象类型 |
| 每行数据 | 对象 |
| 每列 | 属性 |
| 表间关联 | 链接类型 |
| 读写操作 | 动作类型 |

**关键特性**：动作类型让业务用户直接修改数据，改动写进独立的回写存储，不污染原始数据。

### 阶段 5：逻辑 + 动作

- **逻辑**：自动推导新信息。如事件时长 = 结束时间 - 开始时间
- **动作**：四部分——参数输入 + 执行规则 + 前置条件 + 副作用。全程可追溯

## 增量更新

不每次全量重算，而是三层配合：
1. 数据同步：只拉取新数据
2. 管道：只处理新增行
3. 语义层：只更新有变化的对象

**两个踩坑点：**
- 状态变更用 append 同步会出现新旧版本共存 → 管道里做去重只保留最新状态
- 语义层界面修改立即可见，管道批量更新定时跑，两个来源有时间差

## 宽表处理

企业系统导出的常是一张几百列大宽表。关键约束：**一个对象类型只能对应一张表**。宽表必须拆成多张聚焦小表（订单表、商品表、物流表），用链接连接。

管道工具有 AI 辅助写拆分代码，但**决定怎么拆、哪一列归哪个实体，需要人来判断**。这是语义工程项目中最贵的部分，也是核心商业模式所在。

## 语义层与普通数据库 Schema 的真正差异

1. **全链路可追溯**：任意字段值可追溯到原始文件的某一行
2. **写回能力**：动作类型通过独立回写存储修改数据，不污染原始数据
3. **应用层直接消费**：不用写 API，AI 和应用直接操作语义层对象

三者合在一起使语义层成为 **Agent 的操作层**，而不只是数据结构目录。
