# AI Agent 记忆系统：十种开源架构的技术路线与选型判据

> 本文由两集视频素材汇编而成，**未做 LLM 改写**，项目事实与数据均来自原视频口述（原始出处见 `sources`）。

## 一、问题定位：为什么 Agent 需要专门的记忆层

LLM 的默认形态是**无状态**：每次新对话都从零开始，早期用户偏好丢失，对话之间没有继承关系。上下文窗口有限，"把所有东西塞进窗口"在长任务里不成立——视频中引用的实证结论是：**现有 LLM 的"有效上下文长度"远小于其标称值**，同时从长上下文中检索信息并执行推理几乎不可能完成。

于是记忆层要解决的不是"把东西存哪"，而是三个递进问题：

1. **记什么**（抽取、结构化、去重）
2. **怎么取**（检索策略、分层加载、Token 成本）
3. **怎么用**（召回后如何进入推理——被单独点名为"被所有项目忽略的盲区"）

## 二、十种系统的定位（按"记忆在架构中的角色"分层）

| 层次 | 系统 | 一句话定位 | 核心机制 |
|:---|:---|:---|:---|
| **记忆操作语言** | Text to Mem | 给所有记忆系统定义一套通用操作语言 | 12 个原子操作（ENC/RET/STO 三阶段）收敛成 5 元 JSON 契约；`DryRun`+`Confirmation` 双安全闸；JSON Schema + Pydantic 两层校验 |
| **记忆中间件** | Mem0 | 工程化全家桶（最流行的开源记忆框架） | 三层 + 五大工厂（LLM 17 家 / Embedding 11 家 / 向量库 22 种 / 图存储 4 种 / Rerank 5 种）；UUID 幻觉处理；向量+图**双存储并行**；用户/agent/运行时三层隔离 |
| **操作系统式治理** | MemOS | 把记忆当作 OS 一等公民资源来治理 | 6 层架构（API/Core/Scheduler/Cube/Store/基础设施）；三类记忆（文本 / 激活 KVCache / 参数 LoRA）；Redis Streams + RabbitMQ 异步调度 |
| **虚拟内存式 Agent** | Letta（前身 MemGPT） | 把 OS 虚拟内存搬进 Agent 架构 | 三层记忆（Core 常驻 / Archival 归档 / Recall 召回）；block 字符上限**强制压缩**；**Git 作为记忆真实来源**（每次变更一次 commit）+ MEMFS 目录树；Sleep-time Agent 后台自改进 |
| **文件即记忆（用户主权）** | Rimi | 记忆存成可读 Markdown，控制权还给用户 | 文件记忆（短期）+ 向量记忆（长期）双轨；**Delta 增量监控**（纯追加只处理新增，省 92% 调用）；Window/Content 分离嵌入提升召回 |
| **主动型记忆 Agent** | MemU | 记忆自己成为一个 24×7 运行的 Bot | 双 Agent 架构（主 agent + 后台 Memory Bot）；文件系统隐喻映射到库表；**Significance-Aware**：检索次数加权，越常用越易召回 |
| **文件系统式上下文** | OpenViking | 用"文件系统"范式组织上下文（自称"上下文数据库"） | 虚拟文件系统三目录（resources/user/agent）+ 标准 Ls/Find/Mv 操作；**L0/L1/L2 分层加载**（100 token 摘要 → 2000 token 概览 → 全文）；Best-First-Search 检索 + 分数传播 |
| **学习型记忆（认知科学三层）** | Hindsight | 让 Agent"学习"而不只是"记住" | 三层认知架构（World Fact 语义 / Experience Fact 情景 / Mental Models 程序）+ Observations 中间层；Retain/Recall/Reflect 三操作；**四路并行检索**（向量+BM25+MPFP 图+时间）；**Consolidation** 后台异步合并（类比睡眠记忆巩固）；Disposition 记忆库性格配置 |
| **本地数字孪生** | Second Me | 在本地训练"第二个你"的个性化模型 | L0 情景（文档→Insight/Summary）→ L1 身份画像（SHADE 多面体标签）→ L2 程序记忆（LoRA 微调）；三种数据合成策略；"推理 100% 本地，**训练数据准备需外部 API**" |
| **策略增强层（元学习）** | MetaMem | 不存记忆，只教"怎么用记忆" | 四阶段流水线（采样/自反思/元记忆学习/演化）；**Partial Correctness Filter**（只学"半对"样本）；符号化优化（add/overwrite/delete），不微调任何参数；可叠加在任意 RAG 之上 |

## 三、可迁移的设计思想（与技术选型解耦）

以下六条与具体项目无关，换任何技术栈都成立：

1. **把"取回"和"生成"拆成两个操作**。取回是毫秒级、可缓存、可降级的；摘要/生成背后是一次完整 LLM 推理，延迟高上千倍。混成一个操作就没法分别设超时与缓存策略。
2. **对 LLM 的输出做"不信任但兜住"的双层校验**。外层校验格式结构（Schema），内层校验业务逻辑（类型/约束）。关键写操作再加"先模拟（DryRun）或显式确认"的硬闸——防的是 LLM 抽风生成"删除全部记忆"。
3. **分层加载是省 Token 的主要杠杆**。先给廉价摘要让模型挑，再对少数候选加载全量：报告数据是 Token 消耗可降 92–96%（代价是每次检索多一轮 LLM 调用、增加 0.5–2 秒延迟）。
4. **用文件/目录承载记忆，换取可解释与可审计**。路径即结构（比余弦距离直观）、Markdown 可读可编辑、Git 可回溯且天然带审计记录（谁、何时、为何改）。
5. **记忆写入要有"增量"概念**。全量重算是纯浪费；纯追加型变更可只处理新增部分（报告节省 92% 调用）。
6. **召回频次本身是信号**。被反复召回的记忆加权（"肌肉记忆"），检索排序不应只看语义相似度。
7. **记忆的"使用"层独立于"存储"层**。把"学会怎么用检索结果"做成可插拔策略层，可叠加在任意存储之上，且不微调模型参数（完全可解释的自然语言规则）。

## 四、选型判据（落地时要问的六个问题）

| # | 判据 | 为什么关键 |
|:--|:---|:---|
| 1 | **数据落在哪**：云端 / 自托管 / 本地嵌入式 | 决定了能否用于含敏感主体的工作区（本项目的一票否决线） |
| 2 | **每轮成本**：写入与预取各耗多少次 LLM 调用、多少 Token | 有报告：完整模式每次写入 2–5 次 LLM 调用；Token 随记忆规模**线性增长** → 不适高频实时写入 |
| 3 | **可用性是否"静默降级"** | 外部记忆 provider 的预取有时间上限，超时即跳过该轮记忆——不报错、只是没有，属"机制不工作且不可见" |
| 4 | **可观测 / 可审计** | 文件化、可 diff、可版本控制 vs 机器召回、不透明（出问题难排查） |
| 5 | **工程依赖量** | 多套基础设施（图库/消息队列/关系库）与多语言工具链会把运维成本推高；依赖包数量是硬指标 |
| 6 | **成熟度** | 早期版本（0.1.x）常见关键功能（如重排）仍是 TODO；基准宣传数据要辨别基数（某指标 +2568% 源于基线几乎完全无效，而非系统强） |

## 五、与现有工作机制的关系

- **已有机制覆盖的部分**：文件化、可审计的状态层（事实沉淀 + 时间线）、受控关键词与分层检索、结构化笔记。多个项目的核心主张（文件即记忆 / 可读可追溯）与既有做法同向。
- **真正的增量点（若有需求）**：① 跨会话**经验**自动积累（当前靠手动沉淀）② 后台自动**合并/精化**（当前靠人工维护的"编译事实 + 时间线"）③ **时序检索**（当前按关键词检索偏弱）④ 记忆**使用策略**层。
- **既有短板的更便宜解法**：固定容量上限 → 精简 + 分层下沉；语义召回弱 → 手写语义映射（零依赖、零延迟）。
