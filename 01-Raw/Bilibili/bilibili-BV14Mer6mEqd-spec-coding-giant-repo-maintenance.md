## 核心摘录

> 要点提炼（原文见下节「转写全文」）。

- **背景**：讲者的 coronado（音译，项目真名未确认）项目开发一年多、近 20 万行；前后共 7 人接手过，讲者是核心开发，代码质量由他把关。问题：大型项目里如何 vibe coding 又不降低代码质量、不增加 review 成本。
- **手段一：Spec Driven Development + 把约定固化成 skills**。把最基础的、反复出现的代码约定写进仓库：全局异常、API 编写格式、前后端联调规范、透传、前端 UI 规范。skills 分层写——前端写前端的、后端写后端的，前端 skill 再分 UX 与工程化（框架选择、样板代码）。目的是让 AI 后续产码时**不创造项目里不存在的风格**，从而降低 review 成本。
- **手段二：在代码 skills 里加 rules（纪律/约束）**。明确告诉 AI"什么不需要做、什么不能碰"；把架构在早期就固定下来写进 rules，AI 编码时默认加载，避免生成 bad taste 代码。这两步是**腐化的基本预防**。
- **提示词方法（重点）**：不要手写"用户视角"的宽泛 prompt（例如"给我做个 AI 面试功能，要能追问、最后出报告"）——那是从用户视角描述**看得见的系统**，产品经理/工程师视角的底层细节（模型怎么设计、要不要 AI gateway、简历上传链路、交互 UI/UX）全被屏蔽。做法：**先描述大致方向 → 让 AI 根据你的系统生成提示词 → 一定一定要 review → 再去做任务**。直接用 AI 生成的提示词去跑任务，容易出现"传达难掉头"：任务过度庞杂、噪音多，回头再 review AI 的工作就"类似天方夜谭"。
- **提示词要主动砍**：模型能力越来越强（讲者提 GPT-5.6 / GPT-6 Ostra，上下文很长），吐出的提示词动辄 13–14 个工作点，人 review 都要半天。建议砍到 **4–5 个工作点**，方便人机 review、保持代码可控。
- **人的定位要往上走**：人从底层细粒度工作"收出来"，不要把精力下沉到很精细的活。
- **人的大脑容量有限**：20 万行代码，记不住每个模块每个功能的代码、也记不住每个 API 与下游的调用关系——这正是需要"描述方向 + AI 生成提示词 + 人工 review"的原因。
- **陌生领域/框架的坑**：第一次做的系统、第一次用的框架，网上捞到的 skills 可能有点用，但最后一头雾水；哪怕 AI 给了看似可用的代码，自己没搞懂就不该让它上线（对代码要有敬畏心）。所以**不要太关注框架 API 层**（如 Spring Boot 的依赖注入、AOP 这类语言特定 API 与框架细节）。
- **记忆系统设计（AI 面试系统为例）**：分两层——① **长期记忆/画像**：对话中提取的用户信息，大模型识别后调用 tools 写入画像，后续业务领域再调 Agent 时，通过 tools 解锁过往画像数据（讲者称这是系统核心）；② **会话记录**：每轮 ReAct 过程中与大模型的交互、用户提示，都在 session 里。
- **上下文自治理机制**：上下文窗口固定大小，超出会出现信息遗漏与**上下文漂移**；为此开发了自治理机制做**分区压缩**，不同部分的记忆压缩算法分层、各不相同，目标是把上下文尽量压在窗口大小内，保证 Agent 运行质量。
- **Hook 的用法**：用 Hook 调用 Hook，把系统 prompt 或 skills 加载进上下文。因为业务领域固定（三个领域），不需要复杂 tools 来做 skills/prompt 加载——只在代码里规定每个领域只能加载对应的 skills，避免"读到整个内部 skill"的问题，这块做得简单。
- **结尾**：需要文档可关注后私信。

大家好，这里是Will，最近一些同学在学习Coronado（音译）这个项目的时候，向我提出了一些问题，比如说，如何高效的进行vibe coding，如何在一个大型的项目里面去进行vibe coding的同时保证你代码的质量不会说特别低，然后从而就是减少一些review的一些工作。

然后因为Coronado的项目它开发周期有一年多，然后等过代码行数快20万行，所以说整个项目还是比较重的，所以说我觉得这个问题是一个非常非常重要的一点，就是如果你需要学习这个项目的话，这个问题是一个非常非常重要的一点。

如何在这种大型的项目进行vibe coding是一个比较复杂的问题，因为大型项目有很多，每个项目的代码程度、代码腐化程度都不太一样，所以说我针对我这个项目的话，我来分享一下我的一个经验。

因为我这个项目的话，开发的人数不是特别多，总共前后大概是有七个人接手过这个项目，然后因为我是主要核心开发，所以说整个代码质量还是要由我进行一个把关。

我在开发过程当中大量使用了Spec Driven Development的一个实践，主要就是在一些比较基础的一些代码，比如说全局异常，然后比如说是一些API的一些编写格式，比如说前后端的一些联调的一些规范，然后包括透传，包括一个全局异常处理，还有包括前端的一些UI方面的一些东西，就是我们需要把它用skills固化到我们的一个仓库里面去。

对，就是你让AI帮你去写一个skills，然后分层去写吧，就是前端写前端的skills，然后前端的skills里面又分为UX，还有工程化的方面的一些skills，包括就是框架选择，然后一些就是代码开发的一些样板代码，对，就是你用这些space driven development的一些思想去开发这些skills，就是能够让AI在后续生产代码的时候尽可能的不去说胡编乱造一些项目里面不存在的一些代码风格，从来就是减少你的一个review的一个成本。

同时的话，我非常建议你在代码的skills里面加一些rules之类的一些约束，就是rules，你明确的向AI提出我不需要做什么，然后有什么东西是不能碰的，你可以把项目的架构在早期固定下来，然后写到这些rules里面去了，然后AI在coding的时候他会默认去加在这些skill，然后会读学到这些价格方面的一些rules，就是避免去生成这些bad test的一些代码。

所以说主要是靠这两步来进行一个基本的一个腐化的一个预防。

更深层一点的话，我觉得还需要从一些实操经验上面来进行一些优化，就是大部分人现在开发的话，他的一个prompt，他可能是手写比较多，比如说以我的crown agent的项目为例，比如说我做我的一个AI面试这个项目，我可能会很宽泛的去说，能不能在我的项目里面做一个AI面试的功能，然后它要有什么功能，然后需要有什么上传简历，需要有AI追问，需要有什么最后的一个报告，就是哪怕你提示自己的在场就是这样一套你写下来的话，它就是会出现一个问题，就是你的提示词里面更多的是从一个用户的视角去来描述你所看到的系统，而不是从一个产品经理或者说是一个工程师的角度去去描述这个系统，就会导致就是因为最后这个系统暴露给用户的时候，其实很多底层细节它是屏蔽掉的。

比如说我去做一个这个EMM式的一个功能的话，它可能就是会有很多的一些细节上的设计，比如说这个模型我要去怎么去设计，就是我需要做一个AI的一个gateway，然后这个简历我要怎么去上传，这个简历上传的链路是什么样的，然后包括我的一个整个一个交互的UIUX是什么样的，在什么时候AI面试官会提出问题，会怎么提出问题，会如何提出，呃，如何高效的提出问题，然后整个过程当中有什么可以优化的点。

就是你如果用一些非常宽泛的提示词，它是无法很有效的去描述我刚刚提到的这些比较细致化的一些信息的，就是普通的提示词它是平铺直叙的，它整个语意理解出来是一个很平，你懂吗，就是很平的那种感觉，就是看起来信息很多，但是实际深挖的话，有很多模糊的点。

但是如果说你是以一个产品经理或者说是你是一个工程师的视角去全方面很垂直的把整个功能念录全部处理清楚了，就是从用户点击这个按钮到最后，我们整个系统里面有哪些数据模型做了哪些变化，然后有哪些API，这些API之间是如何交互的，你把这些东西描出好之后，就是你的整个AI开发会非常高效，就是很多时候都能一遍过，就是在你提示之前的标号我情况下都成了一遍过的。

尤其是在你配合那个space driven development的一些操作，包括一些rules，包括一些架构设计之类的，如果你把这些东西早些的架构设计Fixed掉，那么你在与AI的交互工人当中，这些阻碍你认知层面的一些无关紧要的问题就是会被屏蔽掉，你可以像产品经理一样专注于业务功能的开发，而把这些比较琐碎的一些基础的架构设计和业务开发就给下沉掉了，差不多就是这个意思。

所以说你们在平时开发提示的时候的时候，尽量就是要写的垂直，不是写的平铺直叙一点，是要写的垂直一点，有深度一点，一次性尽量只解决一个问题，对，然后解决完问题之后，尽量要做一些e2e测试，或者说让AI帮你review一下，深度review一下，不单单是review这个功能有没有写完，更要review这个功能写出来的代码与那个rules里面的那个代码不是代码架构有没有一些冲突的地方，有没有一些腐化的地方，就是整个review也是比较重要的，对。

一个是这个其实是怎么去写，一个是这个起完之后你要去review，还有一个部分我觉得非常重要的就是一个呃，集成测试，对，就是你的代码如果说想要后期减少你的review成本，我觉得集成测试就是非常重要，就是你在写出一个方法之后，你就需要去把这个方法去叠加到你过往的一些测试用力上面，然后让这些测试用力去帮你，就是快速去判断一下这个代码跟现有的系统有没有冲突，对，符不符合预期，而且现在AI生成这个测试用力就是非常非常迅速，对，所以我觉得就是尽量是以测试用力来代替这个功能review，然后尽量是以e2e测试来代替这个全局联条。

为什么说用e2e测试来代替这个全局联条呢，就是现在AI的话，我觉得他的能力已经发展的就比较成熟了，就包括像是一些codex啊，或者说一些什么其他的一些work body之类的，他们要比较完善的一些computer use的一些技术，他就是能本地把你的服务都起起来，然后你用自然语言输入，他就是能控制你的鼠标和键盘，然后持帮你去走完整个功能的一个全套默克的一个流程，并且还能实时的帮你去修复这些Bug，虽然说Token效果有点高，但是我觉得就是他整体的提效还是不错的。
