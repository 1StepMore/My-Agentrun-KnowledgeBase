今天这个视频我想要来聊一个我最近非常强烈的感受。先说结论：目标编程绝对是未来最重要的 AI 编程方式，甚至我觉得你可以不用学太多的 Vibe Coding 的技巧，但是你一定要学会目标编程。因为它改变的不是写代码快一点的这个事情，它改变的是整个工作流。

以前我们用 AI 编程更多是一问一答式的：你发一个需求，AI 写 10 分钟，然后停下来问你，你要不要确认一下？你要不要来测试一下？你要不要继续？这个模式的主要问题在于，它会要求你一直坐在电脑前面，你就好像一个监控一样，AI 干一个活，你就要看一眼，它推一回，你确认一下。

但是目标编程不是这样的。目标编程是你提前把目标、需求、技术方案全部都确定好，然后你让 Codex 或者其他的 AI 编程工具连续工作十几个小时，甚至是连续工作几天，中间不需要你有任何干涉，最后它给你一个可以验收的版本。这种模式才是真正意义上的解放双手。

那我为什么会有这种感受呢？因为我在过去十天里头，用目标编程的方式开发了 6 款 APP，其中两款已经上线了，其他的也在上架的路上。而且这些都不是随便做的 demo，都是能够解决具体的问题的。

比如我的第一个 APP 是一个快速整理相册的工具，它可以通过左滑删除、右滑保留的方式来快速整理连拍照片。第二个 APP 是一个免费的冥想和专注的 APP。第三个 APP 也是今天要讲的案例，它是一个怎么把你愿望可视化并且放到你的手机桌面上的 APP。第四个 APP 是一个跨平台的语音输入笔记。第五个 APP 是一个像刷抖音一样去了解世界数据的 APP。第六个 APP 是帮助新手更快学会用更厉害的 APP。这些 APP 我基本上都是用目标编程的方式做出来的。

所以我现在越来越觉得，未来真正重要的能力，可能不是你会写某一行代码，而是你能不能把一个模糊的想法变成一个 AI 可以长期执行的目标。

接下来我会演示一下我是如何实现目标编程的。举个例子，我的 AI 语音笔记软件已经在这里运行了一天 21 小时，我的 OneWish 优化已经运行了 8 个多小时。

那目标编程到底是什么？我的工作流很简单：

**第一步：先 Plan。** 也就是先把你模糊的想法变成一个清晰的计划。

**第二步：让 Codex 根据这个目标长时间自主运行。**

这两个步骤看起来很简单，但是真正重要的是，你在开始目标编程之前到底有没有把准备工作给做足。你有没有提前做好竞品调研？你有没有想清楚技术方案？你有没有把验收标准写清楚？你有没有给 AI 一个自己可以测试、自己可以验证的环境？如果你没有提前做好这些，那 AI 跑再久也只是跑个垃圾出来。

AI Coding 这么久，我最大的感受是：不是员工不行，是老板不行。AI 做不好，不是 AI 的能力不行，是你需求没有讲清楚。你要做一个五彩斑斓的黑，那它是肯定做不出来的。

所以目标编程第一步，也是最重要的一步，就是先做好调研以及需求文档。

那我们今天就用 OneWish（以愿）这个 APP 来做个例子。这个 APP 的想法其实是我跟一个朋友 Summer 聊天的时候得来的。他跟我说，他会把自己的愿望写在一张纸上，然后把它具象化。比如说他想去斯坦福演讲，比如说他想举办一个自己的 AI 艺术展，或者去北极看极光。他會把這些願望畫出來，然後貼在鏡子前面，每天看一眼。我当时就想说，那这个事情我能不能用 AI 来做呢？比如我上传一张头像，告诉 AI 我想去斯坦福演讲，那 AI 就帮我生成一张我站在演讲台上的照片，或者是帮我生成一张在北极极光下的照片。而且生成完之后，它可以像一个小组件一样放在我的手机桌面上，这样我每次打开手机就可以看到这个愿望被具象化之后的样子。这个就是 OneWish APP 的一个起点。

但如果我没有用目标编程的话，我可能会直接跟 Codex 讲说：帮我做一个愿望可视化的 APP。那大概率会做得很糟糕。所以在真正开始目标编程之前，我会做几件事情。

**第一件事情，做竞品调研。** 我们来看一下我的聊天记录，我先搜索了一下一些愿望清单的竞品信息，然后看了一下大概的情况，并且判断一下这个方向值不值得做，然后它的 MVP 版本应该怎么实现。你看我们竞品有这么多，说明它是一个真实存在的需求。但是我判断了一下，它还是有机会的。比如说上传一张图，然后就可以生成我在斯坦福演讲的照片，我觉得这个点很吸引人。

那接下来我还把我跟我朋友的语音记录一次性发给他，然后让他生成很多张原型图。他给到了几个方向。但我还不是特别满意，就跟他说能不能再来几个，更 dark 一点。其中我就选择了这个愿景车站，我觉得这个方式很好，但是你不发现它没有人物的吗？那我接下来就把我的朋友的照片发给他，他就生成了一個有具體人物的，這個就是我很想要的一個效果。

那接下来我要决定它的配色。他给出了各种配色版本，并且选出了我最喜欢的这种莫奈式风格。接下来就是讨论 APP 的名称、我的 Slogan 是什么。我最终选择的 Slogan 是：英文是 "One Wish Comes True"，中文是"所見皆如願"。我觉得先想好口号跟宣传语是非常重要的，它会让你有一种感觉，说这个东西到底能不能打动人心。它的核心功能点就是愿望可视化，把愿望放进手机桌面。

好，那核心功能确定之后，我们就可以来开始做原型图跟需求文档了。AI 就开始给出一些功能性的建议，比如说核心痛点是什么，然后我们的新手流程、开场页、效果展示页、风格主题流程等等，它全部都被列出来了。包括一些可能的一些愿望，我们核对没问题之后，我们就可以开始去生成我们的具体的需求文档了。

中间有个小插曲，比如说他给了一个什么行动插件，但我觉得它不是核心功能，我就删掉了。然后他还给了一个完整的原型图，但是这个就没有符合我的要求，那我就跟他说不要管这个丑的原型图，我们先把需求文档写出来。然后他就给到一个完整的需求文档。

这个需求文档写得非常好，一定要带大家来过一遍，这个是我目标编程中最重要的一个东西。它这里写了产品名称，然后一句话定位、产品定义、核心痛点，然后我们产品的边界——哪些不做、哪些要做，我们核心用户是什么、核心的体验循环。接下来是需求文档中最重要的部分，也就是说他把页面结构全部罗列了出来，包括我们的底部、新手引导流程、首页、愿景板、主键。每个页面的需求都详细说明清楚了。总共有 30 多个页面，而且还包括了我们的付费系统的设计、订阅版本的价格等等。

这个需求文档的长度达到两三千行。在我们长时间的目标编程之中，这个需求文档是越详细越好，包括它的主题设置、设置、愿景进度、我们的文案内容，以及我们前面提到的愿景车站这个 UI 的主题视觉方向。需求文档最后还包含了我们的验收标准，比如说我们第一版本必须实现以下的功能。就是我们目标编程中一定要明确的说明了我们最终要拿到的是什么，以及它怎么验收这个事情。

那接下来我们就把需求文档跟原型图发给 Codex，开始我们的目标编程。

接下来有几个很重要的点：

第一个，是把你的需求文档放在一个文档之中给它，因为我们这个需求文档长达几千行，所以最好把它放在一个文件当中。

第二个，是你想要的原型图效果给它。

接下来还有个极其关键的步骤，就是我们要给 AI 提供一个 Harness 的环境。因为我已经之前开发过一个冥想 APP，所以我就直接让它在==基础上去修改，因为==有很多现成的功能可以复用，比如主题颜色、设置页面、中英文翻译等等。对于一些复杂的应用来讲，我是非常建议你是基于一个代码模板，或者基于一个现成的项目去修改。但简单的项目也没有关系，你让它从头写也是 OK 的。程序员的世界里头，我们一般把这东西叫做脚手架，因为它已经提前约定好项目开发的一些规范。所以有条件的情况下，尽可能基于代码模板或者现成项目上去修改，因为你可以少踩很多坑。

第二，其实我们 APP 里头是涉及到 AI 生图的功能，所以我把 API 提前给它，它可以通过这个来调用 DALL·E 3 的模型，让用户上传头像来生成它的愿景图。这个就是你必须提前思考好的事情。比如你希望做一个 AI 类的模型，那你就必须要有接入 AI 模型的地方。如果你要做天气预报的 APP，那你就要提前给它准备一个获取当天天气数据的 API。

我们还有更多的小技巧，比如 Codex 直接可以通过 DALL·E 3 生成我们 APP 所需要的图片。我们后端使用的是 Cloudflare，我们可以直接要求它部署一个网站并且提供这个 API 服务，然后同时给它需求文档，并且简单描述我们需要的是苹果风格，并且参考原型图上面的 UI，让它最终自我截图、自我验证。如果你是做一个离线或者简单的 APP，那你就不需要做这些复杂的工作了。

关于 Harness 还有一个至关重要的步骤，就是给它配置相关的 Skills 跟 MCP。如果没有对应的 Skills 跟 MCP 的话，它相当于是没有专业的开发文档和开发工具的。在 Codex 中安装会比较容易。我们在这里安装插件，因为我们这是一个 iOS 的 APP，所以我们至少要搜索 iOS，把这个插件安装上。插件就包括了它怎么去调用本地的 Xcode 开发工具、怎么去写 SwiftUI。同时我建议安装的插件包括了 Chrome 软件控制插件、产品设计 UI 的插件。要注意这些 Skills 跟 MCP 是要根据项目而定的。比如我们之前开发过一个支持微信支付的 AI 教育小程序，那它所需要的 MCP 跟 Skills 就全部跟小程序开发者工具有关。我们当时用到的脚手架就是 Vue Vite，这个项目用到的 Skills 跟 MCP 就是程序云开发的 Skills 跟 CLI。

如果你不知道要安装哪些 Skills 或 MCP 的话，那最好的方式就直接问 AI 说：我要开发什么样的项目，我需要提前安装哪些 Skills？或者你可以在我们的 Skills 说明文档中，在这里找到推荐的一些 Skills。比如我们这里有些开发的 Skills、设计师的 Skills 等等，你也可以直接上网搜索 Skills，然后搜索 iOS，这里也有一些推荐的 Skills。

回到我们的项目，我们之前做的努力其实就是为给 AI 提供一个 Harness 环境。在这个环境里头，它能够自己跑、自己测试、自己验证、自己导出工具、自己有对应的 API Keys 可以调用。你要让它能够长时间自主运行，你就必须给它提供一个良好的工作环境。好在 AI 还是比较容易满足的。我们这里只是买了一个 200 美元的账户，Token 花费在这个案例中我们用了一周额度的大概 30%，它执行了十几个小时。

好，那所有准备做完之后，我们就可以开始我们的目标编程旅程了。我们要做两个事情：第一个，要选择完全访问，就是给这个员工所有的权限；第二个，记得选择 5.5 超高的模型。那国内的话我就推荐你使用 GLM 5.2 的模型，因为这种长时间运行的任务对于 AI 的智能要求程度是很高的。Codex 的话就推荐用 5.5 的模型，它的 Opus 4.6、4.7 估计没有这么强的长程编程能力。

那接下来就是敲向我们的目标编程的命令：斜杠目标。它会出现一个目标的小标识，我们把内容复制过来，然后记得把需求文档拖动到这里来，把原型图也粘贴进来，然后我们就可以开始点击发送了。

实际上这个 APP 我们让它跑了两轮的目标，第一轮跑了十几个小时，第二轮跑了八个小时。因为现在的编程模式都是给一大堆的需求让它去实现，然后测试完之后又重新列出一大堆的需求再让它跑一次目标编程。然后我跟它的对话量、我的监工量就可以降到了最少。

我们来看一下它实现的情况。它跑了一个半小时，这个网站已经部署了，数据库也部署了，然后它截图也开始了自我检查，已经实现了基本的模块。继续往下，它这个 Logo 也生成了，这一轮就实现了对应的主题。这个执行过程就很琐碎了，输出了非常多的设置，跑了十几个小时。

APP 效果：有在斯坦福演讲、举办 AI 艺术展、去看极光。有愿景板，我可以添加，选择头像，确认位置，选择颜色，选择主题，专属生成。同时还有组件功能。页面包含设置、心愿、语言设置、主题等等，功能非常完整。

在这个案例中，它跑到什么时候停下来呢？它卡在了 TestFlight。因为苹果的 TestFlight 是需要人去登录账号，它才能去上传描述文件之类的。然后我就说给它权限，然后让 Cline 参与操作，让我来登录，帮我把这个 APP 版本发到 TestFlight，然后我在手机上去测试。

这种调试方式有两种：第一种就是一问一答，每次给它返回 Bug 然后让它去修复。第二种是再起一个目标给它。比如我发现了很多问题，然后一次性又写了一个需求文档，写了账号的需求文档（苹果登录、到期时间等），还有发现的一堆 Bug 的汇总，一次性丢给它，再开一个目标让它继续编程。通过这种方式，我就实现了多个项目并行开发，不用一直在电脑面前监控。

最后总结一下：目标编程不是简单的让 AI 多写几行代码，它本质上是一种 AI 跟人的一种新型的合作模式。它要求你先调研、先写计划、先梳理好你的需求、配置环境，再让 AI 长时间运行。它不是完全不需要人，恰恰相反，它对人的要求更高了——你要清楚你的目标，你要拆解你的需求，你要验证你的目标到底是否可行，你要为 AI 创造一个可以自我验证的环境。一旦你把这个事情跑通，你的生产力提升会非常夸张。

当然，如果你也像我一样用目标编程的方式去同时进行很多项目的话，你会烧非常多的 Token。像我过去 30 天烧掉的 Token 大概相当于 1 万美元，总共是 1.2 亿的 Token。

我相信所有 AI 的发展，目标编程绝对是未来最重要的一种编程模式。

## 核心摘录

- **「目标编程 vs 一问一答式」**：一问一答要求你一直坐在电脑前当监工；目标编程要求你提前定好目标/需求/技术方案，然后让 AI 连续跑十几小时甚至几天，最后交付可验收版本
- **核心工作流**：Plan（模糊想法→清晰计划）→ Harness（脚手架+API+MCP+Skills）→ Execute（Codex 长时间自主运行）→ Iterate（新需求文档→新目标）
- **关键前置条件**：竞品调研→技术方案→验收标准→自我验证环境
- **需求文档是核心**：两三千行，包含产品定位、边界、页面结构、验收标准
- **Harness 环境**：代码模板+API Keys+Skills+MCP+自我测试能力，让 AI 能独立工作
- **Token 消耗**：30 天约 1.2 亿 Token（1 万美元），但这个模式可并行多个项目
