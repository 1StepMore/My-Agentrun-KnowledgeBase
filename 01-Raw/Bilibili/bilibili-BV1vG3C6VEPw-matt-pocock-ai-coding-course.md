And understanding this stuff is so fundamental, because if you don't understand it, you're going to end up blaming AI when in fact you're just working against how the models are supposed to work. In this video I'm going to walk through each of these constraints and explain how they affect your usage of tools like Claude Code.

And let's start with the biggest constraint, which is the scaling laws around tokens and the context window. The way that LLMs work is they take input text like this, they split it up, and then they tokenize it into numbers here. You don't really need to know why they do this; I've talked about this in separate videos. But when you get these lists of tokens here, all of the tokens that the LLM can see are its context window. We've only got three tokens here in this very small example, but a typical context window maxes out at around 200,000 tokens.

Now, if we were to add another token to this context window here, you might think, okay, all we gotta do here is just store an extra number in memory, right? But that's not quite right. Not only are we storing the actual token in memory, we're also storing all of its relationships to every other token. So for four tokens, that means six relationships. For eight tokens, we've immediately scaled up to 28 relationships. And if I were to draw a hundred tokens here, that would mean roughly 5,000 arrows here. In other words, every time we add a token, the number of things the LLM has to track and keep hold of scales quadratically. It's not like appending a character to a document; it's like adding a team to a football league, where the number of games played massively increases as you add teams.

Now what this means in practice is, as you're using your coding agent, as you're adding more messages to the context window, you are really putting a huge strain on the LLM. And this means, as you fill up the context window, the model will start to struggle, and you end up in what I call the dumb zone. In the smart zone, early in the context window, the LLM has lots of memory to spare, its attention relationships are not very strained, and it can reason really clearly. It can attend to all the information in its context window, and in general it makes smart decisions. But later, when it starts getting a little bit more strained, it goes up into the dumb zone. This is where hallucinations start to creep in, reasoning gets a lot worse, and sometimes it will struggle to recall information that's just sitting there in its context window.

Now where this dumb zone actually starts is a matter of some controversy, and it will probably change over time, but I start getting paranoid around the 40% mark. In other words, in a 200,000 token window, I would start getting scared around the 80,000 token mark. Some might say this is too aggressive, and that maybe 60% or 70% is where the dumb zone starts, but everyone agrees that it does exist, and whenever you're using LLMs you need to bear it in mind.

Now the smart zone and dumb zone is the main constraint that we're going to be working against throughout this entire course, really, but I wanted to mention some others, because they really inform how you use LLMs too. If any decisions are created inside that grilling session, then we need to turn them into ADRs. So the way this will often work is I will grill with the agent, we'll talk about the glossary, we'll hammer out any new terms that need to be added, and then we'll add any ADRs. And then I'll turn that into a commit that I commit to the repo, and then we'll create the product requirements document on top of that. But you might be thinking that sounds pretty annoying having to remember yourself to create ADRs or to hammer out this glossary every single time, surely the skill could handle that for me. Well, guess what? There is a skill for that.

This is my Grill with Docs skill, which essentially runs a grilling session but has a little bit of extra stuff for creating a context.md here, which is the glossary, and also for creating ADRs. This is essentially a drop-in replacement, and this is now what I'm using for every single code base that I have. Every time I'm working in code, I will tend to use Grill with Docs. And every time I'm just doing non-code stuff, I will use Grill Me instead.

You can see that in the instructions for the skill, we have instructions for updating context.md, our glossary, and also offering ADRs, and only creating ADRs when the decision is hard to reverse, surprising without context, or the result of a real trade-off. It also has some context pointers in here to a context format that sort of ties down the format, and also the ADR format too, so the template for the ADR. Overall, I found that Grill with Docs is just an extremely useful skill and adds that extra layer that's needed to answer the most confusing questions for the agents easily in the codebase. ## 核心摘录

### 课程主旨
Matt Pocock《AI Coding for Real Engineers》完整课程（第2期）。核心主张：**开发者应拥有自己的流程（own your process）**，用真实工程技能 + 30 年行业经验沉淀的启发式方法驾驭任何 coding agent，而不是依赖复杂的第三方框架。

### 七阶段 AI 开发流程（课程骨架）
1. **Grilling（访谈/盘问）**：用 agent 拷问想法、强化概念
2. **Research（研究）**：探索第三方 API、工具、备选方案
3. **Prototyping（原型）**：快速验证技术问题，可中途暂停 grilling 去做
4. **PRD（产品需求文档）**：把方向写成文档（团队可审查）
5. **Issues（任务拆解）**：PRD → 带阻塞关系的任务
6. **Implementation（实现）**：**AFK（away from keyboard）模式**——agent 自主完成，人机并行
7. **Review（审查）**：对照 PRD 验收 + 反思流程、更新 skills

### 关键概念
- **AFK 模式**：实现阶段完全无人值守，人类规划 while AI 交付——并行化的核心
- **Deep Modules（深模块）**：来自《Philosophy of Software Design》(John Ousterhout)。小接口 + 大实现。AI 能快速读懂接口 → 高效导航代码库；同时降低人类认知负担
- **AX（Agent Experience）> UX**：Greenfield 项目第一个 PRD 应先定义"agent 体验"——反馈循环、技术选型、模块形状、测试策略
- **Grill with Docs**：Grilling + 建立 context.md（共享术语表）+ ADR（架构决策记录）——回答 AI 无法自行回答的两个问题："为什么这样做"（ADR）和"XXX 是什么"（术语表）
- **Improved Code Base Architecture skill**：探索代码库找浅模块 → 用户选候选 → 并行设计多个接口 → 推荐/混合 → 生成重构 RFC → 转 Kanban
- **2PRD skill 的模块意识**：写 PRD 时预先规划"要构建/修改的主要模块"，主动找可隔离测试的深模块

### 工具链
- 课程 playground：20,000 行代码（TypeScript + Node + React），`pnpm reset` / `cherry-pick` / `pnpm pull` 三个命令管理课程进度
- 模型建议：Opus 4.6（Max 订阅）或 Sonnet 4.6（Pro），**不用 Haiku**；medium effort

## 个人解读

这个课程的核心方法论与我们的 AutoInfo/AutoMedia 实践高度同构：
- **七阶段流程 ≈ 我们的"评估→提issue→子agent修复→验证→迭代"闭环**（用户已沉淀的工作流）
- **AFK 模式 ≈ 我们正在用的 Atlas/Sisyphus 子 agent 大规模实施**
- **Deep Modules ≈ 我们 skills 整改时"拆大 skill 为可独立测试模块"的工程原则**
- **Grill with Docs（术语表 + ADR）≈ 我们 _keywords.yaml 受控词表 + 决策记录**——英雄所见略同

值得借鉴的增量：
1. **ADR（架构决策记录）**：我们 issue 系统有记录，但未系统化为"代码库内 ADR 文件"
2. **AX-first Greenfield 流程**：新项目先定义 agent 体验（反馈循环/模块形状/测试策略）——对我们新建代码库项目有直接参考价值
3. **pnpm reset 式课程状态管理**：可复用到我们的教学/交接场景
