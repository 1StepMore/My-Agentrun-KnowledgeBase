# 智能体与工作流模式（方法论）

> **L3 方法条目**。基于 **E1 官方原文** `building-effective-agents`（2024-12，已被业界引用最多的一篇；官方注明部分工具生态已演进，现行做法见 Claude Managed Agents）；组织与中文表述为**我们的提炼**。

## 一句话

> **最成功的实现用的是"简单、可组合的模式"，而不是复杂框架。** 官方核心建议：**先找最简单的解法，只在确有必要时才增加复杂度**——"这可能意味着**根本不建智能体系统**"。

## 一、关键区分：Workflow ≠ Agent（官方架构区分）

| | **Workflow（工作流）** | **Agent（智能体）** |
|:---|:---|:---|
| 控制流 | LLM 与工具按**预定义路径**编排 | **模型自己决定**怎么走、走几步 |
| 代价 | 可预测、一致 | 更灵活，但**换延迟与成本** |
| 适用 | 任务定义清晰 | 需要灵活性与模型驱动的决策 |

**取舍原则**（官方原话）：agentic 系统是**用延迟和成本换任务表现**——要判断这笔交换划不划算。

## 二、基础构件：增强型 LLM（augmented LLM）

最小单元 = **LLM + 增强件（检索 / 工具 / 记忆）**。当前的模型能主动使用这些能力（自己生成查询、选择工具、决定何时检索）。

## 三、五种工作流模式（官方给的生产实践清单）

| 模式 | 怎么走 | 典型场景 |
|:---|:---|:---|
| **提示链（prompt chaining）** | 拆成多步，前一步输出喂后一步 | 每步可独立验证的任务 |
| **路由（routing）** | 先分类，再分派给专门处理 | 输入类型差异大、可分类 |
| **并行（parallelization）** | 同时跑多份后汇总（或投票） | 需要多视角 / 提速 |
| **编排-工作者（orchestrator-workers）** | 主 agent 动态拆解任务，分派给工作者再汇总 | 子任务数量与内容**事先不确定** |
| **评估-优化（evaluator-optimizer）** | 一个生成、一个批判，循环到达标 | 有明确评价标准、迭代能改善 |

**最后才是 Agent**：模型在循环里自主使用工具。官方强调这些模式**不是规定**，是可组合的构件；**关键是测量表现并迭代**——"只在复杂度能**可证明地**改善结果时才加"。

## 四、关于框架（官方提醒）

框架（Claude Agent SDK / Strands / Rivet / Vellum 等）能简化起步，但**会额外加一层抽象，遮蔽底层提示与响应**——出问题时难以定位。官方倾向：**先用最直接的方式理解和实现**，再考虑框架。

## 五、与本库实践的对应（E3）

| 官方模式 | 我们的用法 |
|:---|:---|
| 评估-优化 | 写审分离（写正文 → 审方向）、质量门 |
| 编排-工作者 | 子代理批量研究（分批写盘、上下文自包含） |
| 提示链 | 分层管线（Raw → Draft → Wiki，每层可独立验证） |
| "只在可证明改善时才加复杂度" | 反对一上来就多智能体/多框架；先跑通再加 |

## 六、实操清单

- [ ] 我这个任务**真的需要 agent**，还是固定 workflow 就够？
- [ ] 我给它的复杂度**有证据支撑**吗？（还是"看起来很先进"）
- [ ] 用了框架吗？出问题时能不能**看到底层提示与响应**？
- [ ] 五种模式里，我该用哪一种？还是**组合**？
- [ ] 复杂度的收益**量过**吗（成功率、耗时、成本）？
