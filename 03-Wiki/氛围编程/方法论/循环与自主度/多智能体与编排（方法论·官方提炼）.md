# 多智能体与编排（方法论）

> **L3 方法条目**。来源为 **E1 官方原文** `multi-agent-research-system`（已入库 `01-Raw/VibeCoding/anthropic-eng/`）。组织与中文表述为**我们的提炼**。

## 一句话

> **多智能体的收益来自"可并行 + 可隔离"，代价是"协调复杂度爆炸"。** 官方原话：多智能体与单智能体的关键差别在于**协调复杂度的快速增长**。

## 一、什么时候值得用（官方判据）

研究类任务的本质：**开放性问题，事先无法预测需要哪些步骤**——"你没法为复杂的探索硬编码一条固定路径"，过程本身就是动态、路径依赖的，人会**根据中途发现不断调整方向**；需要模型**自主运行很多轮**，依据中间结果决定下一步。

> 官方结论：**"线性的一次性管线（one-shot pipeline）处理不了这类任务。"**

## 二、架构：orchestrator-worker（编排-工作者）

- **主 agent（lead）**：分析查询 → 制定策略 → **并行派生多个子代理**
- **子代理**：用检索工具**迭代过滤**信息，**只把结果清单回传**给主 agent，由主 agent 汇总

> 🔑 关键理解：**子代理是"智能过滤器"**——回传的是**压缩后的结论**，不是原始材料。这正是"子代理的首要理由是隔离上下文"的具体形态。

## 三、官方踩过的坑（一手教训，很值钱）

| 早期错误 | 官方修法 |
|:---|:---|
| **给简单查询派生 50 个子代理** | 按查询复杂度决定规模 |
| **无止境地检索不存在的来源** | 设定检索预算/上限 |
| **子代理之间用过量更新互相干扰** | 约束通信内容与频率 |

官方强调的方法论：**"像你的 agent 那样思考"（think like your agents）**——用完全相同的提示与工具**建模拟器，逐步观察 agent 干活**，失败模式会立刻暴露。**提示工程是修这些行为的首要杠杆。**

## 四、评测的独特困难（官方点明）

传统评测假设"给输入 X → 应走路径 Y → 得输出 Z"。**多智能体不这样工作**：即使起点相同，agent 也可能走**完全不同的合法路径**（一个查 3 个来源，一个查 10 个；用不同工具得到同一答案）。

→ 官方结论：**不能检查"是否走了预设的正确步骤"，必须用更灵活的、面向结果的评测。**

## 五、生产可靠性的三条硬经验（官方）

1. **小改动会级联成大行为变化**——传统软件里一个 bug 影响一个功能；agentic 系统里**微小修改会放大成行为巨变**。
2. **错误会累积（errors compound）**：agent 是有状态的，会跨大量工具调用长期运行 → 需要**持久化执行（durable execution）**并沿途处理错误。
3. **不能"从头重跑"**：重启对用户既昂贵又挫败 → 必须做**从出错点恢复（resume from where it was）**。

> ✅ **这一条直接验证了我们的"子代理批处理 + 分批写盘"做法**——我们为了"防超时丢成果"做的分阶段写盘，本质就是官方说的 durable execution + resume，方向一致。

## 六、与本库实践的对应（E3）

| 官方经验 | 我们的对应物 |
|:---|:---|
| 拿不准是否值得用多智能体 | 先问"单 agent + 固定流程行不行"（官方：只在可证明改善时才加复杂度） |
| 子代理回传压缩结论 | 子代理任务要求"最终只返回摘要"，避免中间数据灌回主上下文 |
| 早期 agent 乱派生 | 批处理拆批有明确批数与边界 |
| durable execution / resume | **分批写盘**、断点续跑（`doc_ingest.py --resume` 等） |
| 面向结果的评测 | 交付物验收（文件齐全/编号连续/引用有效）而非"步骤对不对" |

## 七、实操清单

- [ ] 我真的需要多智能体吗？（固定流程能解决就别上）
- [ ] 子代理**回传的是压缩结论**，还是原始材料？
- [ ] 有没有**检索/派生预算上限**？（防"50 个子代理"）
- [ ] 子代理之间的通信**有没有约束**？（防互相干扰）
- [ ] 中途失败能**从断点恢复**吗？还是要从头重跑？
- [ ] 评测是**面向结果**的，还是在检查"步骤对不对"？
- [ ] 我有"像 agent 那样思考"的**观察手段**（日志/模拟）吗？
