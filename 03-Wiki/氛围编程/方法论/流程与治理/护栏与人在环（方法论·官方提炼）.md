# 护栏与人在环（方法论）

> **L3 方法条目**。来源为 **OpenAI 官方 Agents SDK 文档**（E1，官网对本站 IP 403，取自官方 GitHub 仓库 `openai/openai-agents-python/docs/`）。组织与中文表述为**我们的提炼**。

## 一句话

> 问题不是"要不要限制 agent"，而是**在哪一层拦、什么时候拦、谁来批、状态放哪**。

## 一、护栏分四层（官方分类）

| 层 | 拦什么 | 官方例子 |
|:---|:---|:---|
| **输入护栏** | 用户输入 | 用**便宜快模型**做前置检查：恶意用法直接拒绝，省下昂贵模型的调用 |
| **输出护栏** | agent 产出 | 输出是否越界/不合规 |
| **工具护栏** | 具体动作 | 敏感工具调用前校验 |
| **工作流边界** | 整体流程 | 划定 agent 允许活动的范围 |

## 二、执行模式的关键取舍（官方点明）

> **阻断式（blocking）能保证"昂贵的模型根本不会启动"；并行式（parallel）时，昂贵模型可能已经开始跑了。**

→ 这是**成本与延迟的取舍**，不是技术细节。要省钱就阻断，要省时就并行——**必须显式选**。

## 三、Tripwires（触发即中止）

护栏命中时触发 tripwire，**立即中止执行并抛出错误**（而不是"记个日志继续跑"）。设计含义：**护栏要有咬合**——不能只是观测。

## 四、人在环（HITL）的官方机制

| 机制 | 官方说法 |
|:---|:---|
| **工具声明需要批准** | 工具自己声明"我需要人批"（而不是靠外部规则猜测） |
| **运行结果以"中断"暴露** | 待批项作为 interruption 暴露出来，人能看见"卡在哪、等什么" |
| **可序列化 + 可恢复** | `RunState` 让你把暂停的运行**存下来**，批准/拒绝后再恢复 |
| **审批面是"运行级"的** | 不限于当前顶层 agent——**经 handoff 到达的、嵌套 `as_tool()` 的 agent 同样适用** |
| **长时审批** | 审批可能等很久 → **状态要放服务端**（不是进程内存） |
| **自定义拒绝消息 / 自动批准规则** | 拒绝要能说明原因；重复性决策可自动批 |

## 五、与本库实践的对应（E3）

| 官方机制 | 我们的对应物 |
|:---|:---|
| 输入护栏用便宜模型 | 低级推理走免费/廉价档（AMD/GLM），主模型只做高价值判断 |
| 护栏要"有咬合"（tripwire 中止）| 门禁是**阻塞项**（exit≠0 就拦），不是"警告一下" |
| 工具声明需批准 | `human-override-list` 的强制人工签核清单 |
| 状态放服务端 | 长任务的状态**落盘**（`/goal`、handoff 文档、任务卡），不留在上下文里 |
| 运行级审批面 | 子代理/嵌套调用同样受门禁约束（不能"换一层就绕过"）|

## 六、实操清单

- [ ] 我的检查**在哪一层**？（输入/输出/工具/流程）
- [ ] 护栏命中时是**真的拦住**，还是只记日志？
- [ ] 需要人批的动作，是**工具自己声明**的，还是靠人记着？
- [ ] 审批可能等很久时，**状态存在哪**？进程重启还在吗？
- [ ] 嵌套/子代理调用时，护栏会**失效**吗？
- [ ] 省成本 vs 省延迟，我**显式选过**吗？
