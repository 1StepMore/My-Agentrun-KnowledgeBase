# 事故复盘与可观测性（方法论）

> **L3 方法条目**。来源 **E1 官方原文** `a-postmortem-of-three-recent-issues`（2025-09，已入库 `01-Raw/VibeCoding/anthropic-eng/`）。组织与中文表述为**我们的提炼**。
> 🔑 这篇的价值不在"他们出了什么 bug"，而在**"为什么没早发现"**——那部分对我们直接可用。

## 一、背景：多平台等价是个真问题

Claude 同时跑在 **AWS Trainium / NVIDIA GPU / Google TPU** 三种硬件上，通过**自营 API、Bedrock、Vertex AI** 三条通路服务。

> 官方做法：**对模型实现有严格的"等价性标准"**——*"用户不管从哪个平台拿到请求，都应该得到同样质量的回答。"*
> 代价：**任何基础设施变更都需要在所有平台与配置上小心验证。**

## 二、⭐ 为什么难发现（三条结构性原因，最值得抄）

| 原因 | 官方原话要点 |
|:---|:---|
| **① 评测没覆盖用户报的现象** | 他们的验证依赖 benchmark + 安全评测 + 性能指标，还有"金丝雀"小流量先上；但——**"我们跑的评测根本没有捕捉到用户报告的质量下降"**。官方给的解释很关键：**"部分原因是 Claude 常常能从孤立错误中自行恢复"**（→ 单点错误被"自愈"掩盖，指标上看不出来） |
| **② 隐私与可调试性天然冲突** | 内部的隐私与安全控制限制了工程师**何时、能否访问用户与 Claude 的交互**；"这保护了用户隐私，但**使工程师无法查看那些出问题的交互，从而无法定位或复现 bug**" |
| **③ 多个 bug 相互叠加** | 三个问题（上下文窗口路由错误 / 输出损坏 / XLA:TPU 误编译）**重叠出现**，互相掩盖 |

## 三、官方改了什么（三条，可直接当检查项）

1. **更敏感的评测**：开发出**能更可靠区分"正常实现"与"坏实现"**的评测，并持续改进以盯住模型质量。
2. **在更多地方跑质量评测**：虽然平时也在系统上跑评测，但**要在真实生产系统上持续跑**（才能抓到像"上下文窗口负载均衡错误"这类只在生产暴露的问题）。
3. **更快的调试工具**：开发能在**不牺牲用户隐私**的前提下，调试"来自社区反馈"的问题的基础设施与工具。

## 四、与本库实践的对应（E3）——三条都能对上

| 官方教训 | 我们的对应（本晚真实发生） |
|:---|:---|
| **评测没捕捉到用户报的现象** | 我们踩过同一坑：**门禁"假绿"**（装了但空转）、cron 投递静默失败两个月、`compile:false` 豁免通道从未生效——**都是"我们的检查没覆盖真实故障"**。修法也一致：**正负样本自验证**（造违规样本必须被拦 + 造合规样本必须放行） |
| **"能从孤立错误中自行恢复"掩盖问题** | 我们的对应：**单次成功不能当证据**（LLM 判定要多次/交叉；一次跑绿 ≠ 稳定） |
| **隐私限制让工程师看不到问题现场** | 我们的张力：**要留存现场**（原始材料进 Raw、日志落盘、失败样本收集），否则无法复现——这正是我们坚持"Raw 层无损保留"的另一个理由 |
| **要在真实生产系统上跑评测** | 我们的 **`--selftest`** 与"在真实产物上验证"（不是只看 `--help`、不只看单测） |
| **多平台等价性标准** | 我们的"跨 profile 核心能力一致"、跨 provider 的统一口径对比 |

## 五、实操清单

- [ ] 我的检查**能区分"正常"和"坏掉"**吗？（还是无论好坏都绿）——**造两个样本试一次**
- [ ] 同一个检查连续跑，结果稳定吗？（不稳定 → 它掩盖问题）
- [ ] 我在**真实产物**上验证，还是只在小样本上？
- [ ] 出了问题我需要什么才能复现？（**现场留存够吗**）
- [ ] 我有一个"用户报的问题 → 立刻变成检查项"的回路吗？
- [ ] 多环境/多通道下，我有没有**等价性口径**（同一件事各环境结果应一致）？
