# 工具规模与检索的上下文治理（方法论）

> **L3 方法条目**。来源为 **E1 官方原文四篇**（均已入库 `01-Raw/VibeCoding/anthropic-eng/`）：`contextual-retrieval`(2024-09)、`writing-tools-for-agents`(2025-09)、`code-execution-with-mcp`(2025-11)、`advanced-tool-use`(2025-11)。组织与中文表述为**我们的提炼**。

## 一句话

> **工具和检索结果都是"上下文税"。** 官方实测：**5 个 MCP server = 58 个工具 ≈ 55K tokens，对话还没开始就烧掉了**；"在 Anthropic，我们见过工具定义占用 **134K tokens** 才开始干活"。

## 一、问题：工具定义与中间结果的双重税

| 税种 | 官方描述 |
|:---|:---|
| **定义税** | 多数 MCP 客户端**把全部工具定义预先塞进上下文**。多家 server 叠加 → 轻松逼近 100K+ tokens 的固定开销 |
| **结果税** | **中间结果污染上下文**：官方例子——Claude 分析一个 **10 MB 日志**找错误模式，**整个文件进入上下文**，而它其实只需要错误频次摘要 |

## 二、解法 A：工具按需发现（Tool Search Tool）

官方机制：**给工具打 `defer_loading: true`** → 这些工具**初始不加载**；Claude 只看到"搜索工具"本身 + 少数 `defer_loading: false` 的**关键高频工具**；需要时再搜索发现。

**该用/不该用（官方判据）**：

| ✅ 用 | ❌ 不划算 |
|:---|:---|
| 工具定义 **> 10K tokens** | 工具库小（**< 10 个**） |
| 出现**工具选择准确率**问题 | 所有工具**每次会话都要用** |
| 多 server 的 MCP 系统 | 工具定义本身很紧凑 |
| 可用工具 **10+** | — |

> ⚠️ 代价：多一步搜索 → 有延迟，**省下的上下文与准确率提升要能盖过它**才值。

## 三、解法 B：程序化调用（Programmatic Tool Calling）

官方机制：把工具**声明为可被代码调用**（`allowed_callers: ["code_execution_..."]`）→ Claude 写代码调工具，**在代码里过滤/聚合**，只把**结论**送回上下文。

**最受益场景（官方）**：只需聚合/摘要的大数据集 · 三个以上有依赖的多步调用 · **需要在模型看到之前就过滤/排序/转换**的结果 · 中间数据**不该影响模型推理**的任务 · 跨多项并行操作。

## 四、解法 C：用代码执行代替直接调用（code execution with MCP）

官方带来的四个收益：
1. **按需加载工具**（把工具当文件系统上的代码，模型自己读定义）
2. **在数据到达模型前过滤**（避免上面的"结果税"）
3. **隐私保护型操作**（敏感数据不必进模型上下文）
4. **状态持久化与技能**（执行结果可落盘、可复用）

**渐进披露（progressive disclosure）**在这里再次出现：工具可"作为文件系统上的代码"呈现，或提供一个带 `detail_level` 参数的 `search_tools`。

## 五、写好工具描述的官方要点

| 要点 | 说明 |
|:---|:---|
| **命名与描述决定可发现性** | 搜索是按**名称与描述**匹配的：`search_customer_orders` + "Search for customer orders by date range, status, or total amount…" ✅ ／ `query_db_orders` + "Execute order query" ❌ |
| **系统提示里说明"有什么可用"** | 让模型知道存在哪些能力域 |
| **返回值说明要足以写解析代码** | 程序化调用时，模型要照你的说明写解析逻辑 → 字段/类型/取值范围必须写清 |
| **JSON Schema 表达不了"用法"** | schema 能定义类型/必填/枚举，**表达不了"何时该带可选参数、哪些组合才有意义、API 的约定"** → 官方为此加了 Tool Use Examples |
| **命名空间（namespacing）** | 工具多了要分组，降低选择成本 |

## 六、检索侧：Contextual Retrieval + 重排（官方数据）

**问题**：传统 RAG 切块后，块**脱离上下文**就丢义。官方例子：

- 原始块：*"The company's revenue grew by 3% over the previous quarter."* ← **哪家公司？哪个季度？**
- 上下文化后：*"This chunk is from an SEC filing on ACME corp's performance in Q2 2023; the previous quarter's revenue was $314 million. The company's revenue grew by 3%…"*

**做法**：给每个块**前置一段说明性上下文**再嵌入（Contextual Embeddings）+ 建 BM25 索引（Contextual BM25）。

**官方实测数据**（最硬的一条）：**加上重排后，top-20 块的检索失败率从 5.7% 降到 1.9%（降低 67%）**。另外官方指出用**提示缓存**来摊薄上下文化的成本。

## 七、与本库实践的对应（E3）

| 官方要点 | 我们的对应 |
|:---|:---|
| 工具定义税（>10K tokens 就该按需加载） | 本机 **200+ skill** 的 description 也是常驻税 → 官方机制直接说明"该收敛/该按需" |
| 命名与描述决定可发现性 | 我们的 `description` 军规（触发条件前置）在此得到**第二处印证** |
| 中间结果污染 | 子代理批处理要求"只回传摘要"；批处理**分批写盘**而非把数据堆回上下文 |
| 程序化调用（代码里聚合） | 我们用 `execute_code` 处理大批量而非让模型直接读 |
| Contextual Retrieval | 本库 Raw 页**保留原始地址 + 上下文头**，正是"给块加语境"的同类做法 |
| 检索失败率要有数字 | 我们的门禁/校验全部给出**可核对的计数**（阻塞 0 / 命中 N 条） |

### 📊 本机实测（2026-09-23，不是估算）

| 指标 | 值 |
|:---|:---|
| skill 总数 | **204** |
| 常驻字符（全部 skill 的 name + description 合计） | **35,161** 字符 |
| 常驻 token 粗估 | **≈ 11,000 tokens** |
| 全部 SKILL.md 正文合计 | 2.3 MB（**不常驻**，按需读） |
| 最贵的单个 | `automedia-production-guard`（603 字符） |

> 🎯 **结论（对着官方判据看）**：官方建议"工具定义 **> 10K tokens** 时考虑按需发现"——**我们正好压在这条线上**（≈11K）。
> 且官方"不该用"的三种情形我们**都不符合**（工具库不小、不是每个都高频用、定义不紧凑）。
> → 按官方标准，**本机 skill 库已到"该考虑渐进披露"的规模**；下一步要做的是把低频 skill 归档或改成按需加载，而不是继续加。

## 八、实操清单

- [ ] 我常驻的工具/skill 定义**占多少 token**？（量一次，别猜）
- [ ] 有没有"办了 10 次会话却一次没用"的能力在吃常驻预算？
- [ ] 工具/技能描述**能被人和模型"搜到"**吗（名称+描述）？
- [ ] 大数据处理是**让模型直接读**，还是**在代码里聚合后再给结论**？
- [ ] 返回值里**有没有模型根本不需要的字段**？
- [ ] 我的检索有**失败率数字**吗？（没有数字 = 无法改进；官方给了 5.7%→1.9% 这种可核对结果）
