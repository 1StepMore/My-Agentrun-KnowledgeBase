# 上下文工程（方法论）

> **L3 方法条目**。来源为 **E1 官方原文**（Anthropic 工程博客 + Claude Code 文档）；本页的组织与中文表述是**我们的提炼**——引用具体论断请回原文。
> 原文：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents（2025-09-29）

## 一句话

> **上下文是有限资源：找到"最小的、高信噪比的 token 集合"，让模型更可能产出你要的结果。**

这是 Anthropic 给的全篇结论，也是这一层唯一的判据。

## 一、它和"提示词工程"是什么关系（官方定义）

官方定位：**上下文工程是提示工程的"演进"**，不是替代——

| | 提示词工程 | 上下文工程 |
|:---|:---|:---|
| 关注 | 怎么写指令（尤其 system prompt） | **推理时该有哪些 token 存在**（含指令之外的一切：工具定义、检索结果、历史、文件内容） |
| 场景 | 单次分类/生成 | 多轮、长任务、agent 循环 |

## 二、为什么要紧：两条官方机制

1. **Context rot（上下文腐化）**：needle-in-a-haystack 类研究显示——**窗口里 token 越多，模型准确召回其中信息的能力越差**。官方强调这不仅是个别模型的问题，**所有模型都有**（只是程度不同）。
2. **Attention budget（注意力预算）**：LLM 像人的工作记忆一样有上限，**每个新 token 都在消耗这个预算**，边际收益递减。

→ 结论：**"塞得多"不等于"记得住"**。这与"模型变强了就不用管上下文"的直觉相反。

## 三、怎么做：五个杠杆（官方给出的维度）

| 杠杆 | 官方要点 |
|:---|:---|
| **① System prompt 的"正确高度"** | 官方叫 Goldilocks zone：一端是**硬编码复杂脆弱逻辑**（易碎、难维护），另一端是**含糊的高层指导**（模型无所适从）。要"清晰、直接、处在恰好的抽象层" |
| **② 工具设计** | 工具定义本身占 token；工具要**token 高效**、边界清楚（详见官方另一篇 writing-tools-for-agents） |
| **③ 检索方式：从"预先嵌入"到"即时"（just-in-time）** | 早期做法是推理前用 embedding 预检索；现在的趋势是**让 agent 自己按需检索**（agentic search），只在需要时把文件/结果取进上下文 |
| **④ 长任务的压缩（compaction）** | 长跨度任务靠压缩把历史转成摘要继续推进；Claude Code 侧对应 `/compact`，官方同时给了**缓存命中率**这个观测指标 |
| **⑤ 隔离** | 用子智能体（subagent）把"脏活"的中间结果**关在子上下文里**，只回传结论——这是 subagent 被设计的**首要理由**（不是"多一个人干活"） |

## 四、常见错误（对照官方两种失败模式）

- ❌ 把复杂规则硬编码进 prompt 想"精确控制" → 脆弱、维护成本高
- ❌ 只给模糊的高层目标 → 模型自由发挥、结果不稳
- ❌ 把工具输出、检索结果、日志**全量倒进上下文** → 触发 context rot
- ❌ 长任务不压缩、不隔离 → 撞窗口上限后行为崩坏

## 六、实操清单（可勾）

- [ ] 我的 system prompt 处在"正确高度"吗？（有没有硬编码脆弱逻辑 / 有没有太含糊）
- [ ] 每个工具的返回值**默认有多大**？要不要截断/摘要？
- [ ] 长任务有没有**压缩策略**？压缩后关键结论还在吗？
- [ ] 有没有用**子智能体隔离**中间过程，只回传结论？
- [ ] 有没有观测**缓存命中率**与每轮 token 消耗？（无观测 = 无法改进）
- [ ] 有没有一个"最小高信噪比"的**验收标准**：删掉一段上下文，结果变差吗？（不变 → 那段是噪声）
