# Harness 与长任务（方法论）

> **L3 方法条目**。基于 **E1 官方原文**两篇（2025-11 与 2026-03）；组织与中文表述为**我们的提炼**。
> 原文已入库：`01-Raw/VibeCoding/anthropic-eng/`（`effective-harnesses-for-long-running-agents`、`harness-design-long-running-apps`）

## 一句话

> **长任务失败，通常不是模型不行，是 harness 不行。** 官方原话：*"compaction isn't sufficient"* —— 即使把压缩做好了，前沿模型在长任务上"开箱即用"仍会失败。

## 一、长任务的真正难题

不是"单轮不会做"，而是**要跨很多个上下文窗口完成一件长期的事**：

- 跨窗口后**还记不记得目标**（我们的对照：目标漂移）
- 有没有**可核对的进度**（还是每轮重新开始）
- 谁来判定"这算做完了"

## 二、官方给的 harness 组件

| 组件 | 官方做法 | 解决的问题 |
|:---|:---|:---|
| **初始化 agent + "首个窗口用不同提示"** | 第一个上下文窗口专门用来**搭环境**：把后续所有 agent 需要的上下文准备好 | 让后面的窗口"一上手就懂" |
| **功能清单（feature list）** | 显式列出要做的功能 | 治"一口气梭哈整个应用"或**提前宣布完工** |
| **增量推进** | **一次做一个功能**，做完再下一个 | 可验证、可回退、可续做 |
| **交接产物（artifacts）** | 把状态落到**文件**里跨会话传递 | 治跨窗口失忆 |
| **测试** | 每步有可跑的验收 | 治"看起来完成了" |

**社区同源方法**：官方在文中提到开发者收敛到类似做法，如 **"Ralph Wiggum" 方法**——用 hooks/脚本把 agent 按在**持续迭代循环**里。（这正是我们 `/goal` 那套机制的原理来源。）

## 三、关键突破：让**主观质量可评分**

官方在长任务里最难的一环是"自我评估"——尤其前端设计这类主观质量。他们的解法值得单独抄下来：

> *"'Is this design beautiful?' is hard to answer consistently, but 'does this design meet criteria X?' is not."*
> 美学无法完全化成分数，但可以**把设计原则与偏好编码成评分判据**——"美不美"答不了，"是否满足第 N 条判据"答得了。

**推论（适用范围远超前端）**：任何"说不清好坏"的任务，都可以拆成**若干条可判定的是/否判据**。这一步做完，agent 的自我收敛能力才真正成立。

## 四、与本库实践的对应（E3）

| 官方组件 | 我们的对应物 |
|:---|:---|
| 首个窗口搭环境 | 长任务开头的**方向盘点**（任务锚点 + `/goal` 五字段） |
| 功能清单 | 交付物清单 + 待办列表（不写在脑子里，**写在文件里**） |
| 增量推进 | 分批写盘（防超时丢成果）、每批可验证 |
| 交接产物 | `handoff/`、项目页、写入收尾脚本 |
| 测试 | **门禁**（`kb_coverage_check.py` 阻塞项、`--selftest`）＋ 交付前完整性校验 |
| 主观质量可评分 | 把"内容质量"拆成可勾选判据（去 AI 味扫描、事实核查、引用红线、CTA 规则） |

## 五、实操清单

- [ ] 长任务开工时，**目标写进文件/`/goal`**了吗？（只写在脑子里 → 必然漂移）
- [ ] 有一份**显式清单**（要做哪些、做到哪了）吗？
- [ ] 每步有没有**可跑的验收**？还是靠"看着像完成了"？
- [ ] 状态是**落盘**的还是只在上下文里？
- [ ] 遇到"说不清好坏"的验收，我**把它拆成是/否判据**了吗？
- [ ] 中途需求变了，有没有**受影响面盘点**？（列出已有资产逐条判定"仍有效/需改/已被取代"）
