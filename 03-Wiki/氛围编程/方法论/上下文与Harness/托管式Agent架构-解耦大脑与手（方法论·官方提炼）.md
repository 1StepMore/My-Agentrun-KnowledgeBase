# 托管式 Agent 的架构：解耦大脑与手（方法论）

> **L3 方法条目**。来源 **E1 官方原文** `managed-agents`（2026-04，已入库 `01-Raw/VibeCoding/anthropic-eng/`）。
> ⚠️ **这篇是官方"现行做法"**——官方在 `building-effective-agents`（2024-12）里明确指向它作为更新后的方案，所以两篇要对着看，别只引旧的那篇。

## 一句话（官方开篇）

> **"Harness 里编码着假设，而这些假设会随着模型变强而失效。"**
> （Harnesses encode assumptions that go stale as models improve.）→ 所以真正要设计的是**能在 harness 变化时依然稳定的接口**。

## 二、踩过的坑：**别养宠物**

官方最初把**全部组件塞进一个容器**（会话 + agent harness + 沙箱共享同一环境）。好处很实在（文件编辑就是直接系统调用、没有服务边界要设计），但撞上了老问题：

> **"我们养了一只宠物。"**（pets vs cattle：宠物是有名字、需要人手照料、丢不起的个体；牛是可替换的。）

后果：**服务器成了那只宠物**——容器挂了，**会话就丢了**；容器无响应就卡在那里。

## 三、解法：把"大脑"与"手"解耦

拆成三个**互相假设很少、可独立失败/替换**的接口：

| 部件 | 内容 |
|:---|:---|
| **大脑（brain）** | Claude + 它的 harness |
| **手（hands）** | 执行动作的沙箱与工具 |
| **会话（session）** | 会话事件日志 |

关键动作：**harness 从容器里搬出来**，改成**像调用任何工具一样调用容器**：`execute(name, input) → string`。
→ 容器变成"牛"：**容器死了，harness 把它当一次工具调用失败来捕获处理**，会话仍然在。

## 四、⭐ 一条最容易被忽略的区分

> **"会话（session）不是 Claude 的上下文窗口。"**（The session is not Claude's context window.）

官方解释：长任务往往**超出上下文窗口长度**，而处理它的常规手段（压缩、memory 工具写文件、上下文裁剪）**都包含"留下什么、丢掉什么"的不可逆决定**。

> **"对上下文做有选择的保留或丢弃，这类不可逆决定会导致失败。"**

→ **把"会话事件日志"（可持久、可重放、无损）与"模型当前看到的上下文窗口"（有损、压缩、不可逆）当成两个东西**，是长任务架构的关键区分。

## 五、解耦带来的两个额外收益（官方）

1. **能接客户自己的 VPC 资源**：以前必须把网络对等过来（因为容器里的 harness 假设所有资源都在旁边）；harness 出容器后，这个假设就消失了。
2. **性能**：以前"多少大脑就要多少容器"，每个会话都要等容器置备完才能开始推理；解耦后不再按大脑数付容器成本。

## 六、设计哲学（官方结论，值得抄）

> 他们面对的是老问题：**如何为"尚未被想到的程序"设计系统。**
> 操作系统能活几十年，靠的是**把硬件虚拟化成足够通用的抽象**，容得下当时还不存在的程序。
> Managed Agents 是一个 **meta-harness**：**对"Claude 未来需要哪种 harness"不持立场**，只提供**允许许多不同 harness 的通用接口**。（官方举例：Claude Code 就是一个很好的 harness。）

## 七、与本库实践的对应（E3）

| 官方原则 | 我们的对应物 |
|:---|:---|
| 别养宠物（单点容器=会话丢失） | 我们的长任务状态**落盘**（`/goal`、handoff 文档、任务卡）→ 进程死≠任务丢 |
| 会话 ≠ 上下文窗口 | 我们的做法正是这样：**会话记录与当前上下文分离**，关键结论写进文件（Raw/Draft/Wiki、项目页） |
| 不可逆的有损决策要避免 | 知识库的 Raw 层**保留原始材料**（无损），压缩/提炼只发生在 Draft/Wiki → 可回溯 |
| 大卸八块成可替换接口 | 我们的流水线分层（Raw→Draft→Wiki）、检测器/门禁/编译器各自独立可替换 |
| 为"尚未想到的程序"设计 | 本库定位"任何 agent 都能跑的引擎"、skill 只引用不复制 → 同一理念 |
