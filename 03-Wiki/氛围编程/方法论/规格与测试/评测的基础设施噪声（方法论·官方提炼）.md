# Agentic 评测的基础设施噪声（方法论）

> **L3 方法条目**。来源 **E1 官方原文** `infrastructure-noise`（2026-02，已入库 `01-Raw/VibeCoding/anthropic-eng/`）。组织与中文表述为**我们的提炼**。

## 一句话（官方原话）

> **"基础设施配置能让 agentic coding benchmark 摆动好几个百分点——有时比榜首模型之间的差距还大。"**
> 更进一步：**"榜单上 2 分的领先，可能是真实能力差距，也可能只是因为那次评测跑在更肥的硬件上，或者运气更好，或者两者都有。"**

## 一、官方实测发生了什么

Anthropic 在一套 GKE 集群上跑 Terminal-Bench 2.0 做校准，发现两件事：

1. **分数与官方榜单对不上**；
2. **基础设施错误率高得离谱**：多达 **6% 的任务因 pod 错误失败**，且**绝大多数与模型能力无关**。

根因是**资源约束的语义**：容器运行时用**两个独立参数**管资源——**保底分配（guaranteed allocation）**与**硬上限（在此时被杀）**。他们的实现把二者设成相等 → **零余量**，一次瞬时的资源尖峰就 OOM 杀掉容器。

## 二、⭐ 最关键的一条：资源上限会**改变评测在测什么**

| 资源档位 | 官方观察 |
|:---|:---|
| **约 3× 以内** | 增加的资源**只修可靠性问题**（瞬时的资源尖峰）→ **"评测变得更稳定，但并没有变得更简单"** |
| **超过 3×** | 额外资源**开始真的帮 agent 解决它原本解决不了的问题** → **"限制其实会改变评测所测量的东西"** |

推论（官方明说）：**紧的限额在奖励"高效策略"**，**松的限额在奖励"会利用资源的 agent"**——写精简高效代码的 agent 在紧约束下表现好，暴力搜索型在宽松约束下表现好。**同一份榜单在不同资源档下测的不是同一件事。**

## 三、还有哪些隐藏变量（官方列举）

时间上限 · 集群健康度 · 硬件规格 · 并发度 · **出口带宽（egress bandwidth）** · **甚至一天中的时段**（API 延迟随流量和故障波动 → 通过率随之起伏）。

> 官方定性：**"agentic 评测本质上就是端到端系统测试，这个系统的任何组件都可能成为混淆变量（confounder）。"**
> **"『模型能力』与『基础设施行为』之间的边界，比单个 benchmark 分数所暗示的要模糊。"**

## 四、官方的建议

1. **理想**：每次评测都在**完全相同的硬件条件**下跑（评测脚手架 + 推理栈都一样）→ 可复现。
2. **不现实时（现实做法）**：因资源约束有两个参数（保底 + 杀死阈值），**评测应当逐任务同时指定这两个参数，而不是钉一个单一值**。单一值 = 保底等于阈值 = 零余量 = 我们记录的 1× 档的瞬时尖峰就足以打翻评测。
3. **报告要有 setup 配置**：官方强调，"没有公开（或标准化）的环境配置，外部根本看不出差异来自哪里"——**"资源与配置应被视为评测的一等公民"**。

## 五、与本库实践的对应（E3）——这条对本库方法论影响最大

| 官方结论 | 我们的对应规矩 |
|:---|:---|
| 分数差异可能来自环境而非能力 | 我们的比价铁律：**同口径才可比**、禁止不同变体比价、活动/常规双窗口分开 |
| 榜单领先 2 分可能是噪声 | 选型时**不拿几个百分点的差距当决策依据**；要看用途匹配与价格结构 |
| 评测是端到端系统测试，处处是混淆变量 | 我们报告要求**标证据等级与置信度**、区分代码证据与推断 |
| 环境配置要公开 | 我们的调研报告必须**标数据来源与口径** |
| 紧约束奖励高效、松约束奖励利用资源 | 同一 agent 在不同资源/预算下的表现不可直接互推（**跨环境对比要打折看**） |
