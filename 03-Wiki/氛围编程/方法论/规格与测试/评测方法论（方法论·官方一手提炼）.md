# 评测方法论

> **L3 方法条目**。基于 **E1 官方原文** `demystifying-evals-for-ai-agents`（已入库 `01-Raw/VibeCoding/anthropic-eng/`）；组织与中文表述为**我们的提炼**。

## 一句话

> **没有评测的团队会陷在"反应式循环"里：修好一个、打坏一个，还分不清哪个是真回归、哪个是噪声。** 官方原话——评测的价值是"**把'感觉变差了'变成可行动的东西**"（turning "the agent feels worse" into something actionable）。

## 一、什么时候必须上评测（官方的临界点）

- 早期靠**手工试 + 直觉 + 自己吃狗粮**，能跑很远；此时严谨评测"看起来像额外开销"。
- 但**进入生产并开始放量后**，这套会崩：**用户在报"改了以后变差了"，团队却在"盲飞"**，除了猜和试没有办法。
- 官方的结论很硬：**评测是核心组件，不是事后补充**（not an afterthought）；越早投入越快（失败变成测试用例 → 测试用例挡住回归 → 指标替代猜测）。

## 二、评测的基本结构 + 三类评分者

**评测 = 一组任务 + 一套评分者（grader）+ harness（执行框架）**

| 评分者 | 特点 | 用在 |
|:---|:---|:---|
| **代码判定** | 确定性、可复现、便宜 | 能不能编译/测试通过/格式对不对 |
| **模型判定** | 灵活，可判"语义上对不对" | 开放答案、质量类 |
| **人工判定** | 最准、最贵 | 校准前两者、边界案例 |

> **推论**：三者是**组合**关系，不是替代关系。开放集用模型判，但必须用人工样本**反向校准**（我们自己的教训：开放集判定要靠人验样本，不能自评）。

## 三、两个必须区分的评测类别

| | **能力评测（capability）** | **回归评测（regression）** |
|:---|:---|:---|
| 问 | 它**能不能**做到（新的、更难的事） | 它**还做不做得对**（原来会的事别退化） |
| 通过率预期 | 常常**应该低**（在探前沿） | 应该**接近 100%** |
| 用途 | 指方向、量进步 | 挡回归、防倒退 |

**混用这两类是常见错误**：拿能力评测当门禁会天天红，拿回归评测当进步指标会自我感觉良好。

## 四、评测不是全部（官方的方法全景）

自动化评测只是**其中一种**理解 agent 表现的方式。完整画面还包括：**生产监控、用户反馈、A/B 测试、人工看 transcript、系统性人工评审**。官方列了各自的优缺点（自动化评测：迭代快、可复现、无用户影响、可每提交跑；代价是：只覆盖你想到的场景）。

## 五、从 0 到 1 的路径（官方给的路线）

1. **收集任务**，形成初始评测数据集（从真实失败里来）
2. **设计 eval harness 与评分者**（按上面三类组合）
3. 分 agent 类型扩展（编码 / 研究 / 计算机操作 / 对话），别从零发明——官方说这些方法可直接当底座
4. 处理**非确定性**（同一任务多次跑结果不同 → 判据要容纳分布，不是单次）

## 六、与本库实践的对应（E3）

| 官方要点 | 我们的对应物 |
|:---|:---|
| 失败 → 测试用例 | 发现机制缺陷 → 立刻立检查项（如 C8 红线传播、门禁自测） |
| 回归 vs 能力 | 门禁=**回归判据**（必须恒为 0）；探索新能力不能拿门禁当成绩单 |
| 三类评分者组合 | 机械检查（代码判定）+ LLM 判定（去 AI 味/事实核查）+ 人工复核（红线、对外口径） |
| 非确定性 | LLM 判定要**多次/多模型交叉**，不采信单次输出 |
| 评测要能"每提交跑" | git pre-commit 钩子跑 `kb_coverage_check.py --staged` |

## 七、实操清单

- [ ] 我有**明确的失败样本集**吗？（还是每次现编一个）
- [ ] 我的判据里，"必须恒为 0"的**回归门禁**和"看趋势"的**能力指标**分开了吗？
- [ ] 开放集判定有**人工校准**吗？（自评不算证据）
- [ ] 评测能**每次改动都跑**吗？（不能自动跑 = 迟早不跑）
- [ ] 同一任务重复跑，结果稳定吗？（不稳定就先解决这个）
