# 沙箱、隔离与遏制（方法论）

> **L3 方法条目**。来源为 **E1 官方原文**两篇（`how-we-contain-claude`，2026-05；`claude-code-sandboxing`，2025-10，均已入库 `01-Raw/VibeCoding/anthropic-eng/`）。组织与中文表述为**我们的提炼**。

## 一句话

> **先在"环境层"设计遏制，再去"模型层"引导行为。** 官方原话：*"The deterministic boundary is what gets hit when everything probabilistic misses."* —— **决定性的边界，是一切概率性防护都漏掉时最后被撞上的东西。**

## 一、三类风险（官方分类）

| 风险 | 说明 |
|:---|:---|
| **用户误用** | 用户（恶意或疏忽）让 agent 做有害的事——**包括"让 agent 绕过他觉得烦的检查"**、跑不懂的破坏性命令 |
| **模型不当行为** | agent 做了没人要求的有害动作（官方提醒：**模型变强不等于风险变小**——弱模型更多是"看错情况犯明显错"，强模型则可能做出更隐蔽的错） |
| **外部输入** | 见第四节（供应链 + 提示注入） |

## 二、三种遏制模式（官方生产实例）

| 模式 | 隔离强度 | 前提 | 代价 |
|:---|:---|:---|:---|
| **① 临时容器**（claude.ai 代码执行） | 最强：容器 + 文件系统**每次会话即弃**，全在服务端 | 无 | **能力上限也最低**（无持久工作区、碰不到用户文件） |
| **② 人在环沙箱**（Claude Code） | 中：可访问本地文件/Shell/网络，靠**人审批**兜底 | ⚠️ **只有因为用户是开发者才可行**——"他们读得懂 bash、知道 `rm -rf` 是什么" | 用户得有能力判断弹窗 |
| **③ 本地 VM**（Cowork） | 强：整机虚拟化 | 面向**非技术知识工作者** | — |

> 🔑 **模式选择的唯一判据（官方）**：**"隔离强度要匹配用户的监管能力（match isolation strength to the user's capacity for oversight）。"**
> 一个读得懂 bash 的开发者，和一个读不懂的知识工作者，**不是在同一个威胁模型里**。
> 官方举例：不该指望非技术用户去判断 `find . -name "*.tmp" -exec rm {} \;` 这种命令——**当"批准一个例外"需要的专业知识超出了典型用户的能力，管理员就该设成绝对、常开的边界**（而不是弹窗让人拍脑袋）。

## 三、沙箱买来的是"自主度"，不只是安全

官方另一篇的定位很清楚：沙箱（**文件系统 + 网络双重隔离**）的作用是**"减少权限弹窗、同时提高安全性"**。

→ 反直觉但重要：**隔离是自主度的前提**。没有边界的自主 = 靠人盯；有了强隔离，才敢让它跑得更远。用法上：**"让它在盒子里随便跑" 比 "让它自由但处处要批" 生产力更高**（前提是盒子真的是盒子）。

## 四、信任 agent 读的东西（比 MCP 更大的一道题）

官方原话：*"进入 agent 的任何外部资源同时代表两种风险：传统供应链意义上的**代码执行风险**，以及**提示注入向量**。"*

传统依赖审计（锁版本、验签、审源码）**只解决第一种，漏掉第二种**。且——

- **本地安装的工具可审计**（能读代码、锁版本、不会背着你变）
- **远程工具（托管 MCP server、云连接器）不行** → **"远程 vs 本地"比看起来更重要**

## 五、官方总结的三条原则（可直接当检查表）

1. **先环境层，再模型层**：遏制先做成确定性的边界，再谈"让模型更守规矩"。
2. **盯"出口"（egress）**：官方两个最有教育意义的事故（员工钓鱼、第三方白名单泄露）**都是数据经由"被允许的路径"流出**——模型层完全帮不上忙，因为**没有任何异常可供它识别**。
3. **隔离强度匹配监管能力**（见 §二）。

## 六、与本库实践的对应（E3）

| 官方原则 | 我们的对应物 |
|:---|:---|
| 环境层优先 | 门禁写在**机制**里（git 钩子/脚本），不靠"我记得检查" |
| 决定性边界兜住概率性失效 | 门禁是**阻塞项**；LLM 判定只作补充（概率性的东西不单独承重） |
| egress 风险（数据从被允许的路径出去） | 对外材料的**红线清单 + 禁外引标记**——正是"允许路径上的泄漏"防护 |
| 用户误用（"绕过他觉得烦的检查"） | 门禁不可在会话内绕过；重大改动要先自查必要性 |
| 隔离强度匹配监管能力 | 低级批量判断走免费档（可以更自主）；主线决策走主模型（更保守） |
| 外部资源 = 供应链 + 注入双风险 | 引入第三方 skill/MCP 前要评估（外部 skill 是权限面） |

## 七、实操清单

- [ ] 我的**决定性边界**是什么？（一切概率性防护失效时，撞上的是什么）
- [ ] 我是不是把安全寄托在"模型会更守规矩"上了？
- [ ] 数据可能从**哪条被允许的路径**流出去？（egress 视角）
- [ ] 我给 agent 的隔离强度，和**我自己的监管能力**匹配吗？
- [ ] 引入外部 skill/MCP 时，我评估**提示注入**了吗（不只是代码安全）？
- [ ] 有没有"绝对、常开的边界"来替代"每次都靠人拍脑袋批准"？
