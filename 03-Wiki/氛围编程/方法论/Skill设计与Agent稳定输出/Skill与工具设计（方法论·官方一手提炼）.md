# Skill 与工具设计（方法论）

> **L3 方法条目**。基于 **E1 官方原文**（Anthropic 工程博客两篇）；本页组织与中文表述为**我们的提炼**。
> 原文：`equipping-agents-for-the-real-world-with-agent-skills`（2025-10-16）、`writing-tools-for-agents`（2025-09-11）——均已入库 `01-Raw/VibeCoding/anthropic-eng/`

## 一句话

> **Skill 是"过程性知识"的载体；工具是"行动的接口"。两者都吃上下文预算——所以设计的核心不是"功能多全"，而是"该在什么时候、以多少 token 出现在模型面前"。**

## 一、Skill 是什么（官方定义，机制层）

- 最简单形态：**一个目录 + 里面一个 `SKILL.md`**，文件开头是 YAML frontmatter，必填 `name` 和 `description`。
- ⚠️ **关键机制**（解释了所有 skill 写作军规）：**agent 启动时会把所有已安装 skill 的 name + description 预载进系统提示**。这是"**渐进披露（progressive disclosure）的第一层**"——只给足够让模型判断"要不要用"的信息，正文按需再读。

> **推论（本库军规的根因）**：既然 description 是常驻成本 + 唯一的选择依据，它就必须**自包含触发条件**（"什么时候用我"），而不是功能简介。我们自己的规矩"description 前 57 字符摆触发条件"，根因就在这里。
> 另一个推论：**skill 装得越多，常驻成本越高**——这是"skill 数量要有预算意识"的机制原因。

## 二、Skill 怎么写（官方四条）

| 官方建议 | 落地含义 |
|:---|:---|
| **从评测出发**：跑代表性任务，看 agent 在哪卡住/缺上下文，再增量补 skill | 不要先想"我要写个什么 skill"，而是**先看失败点** |
| **为规模而结构化**：`SKILL.md` 膨胀时拆成多个文件并引用；**互斥或很少同时用的内容分开存**，能省 token | 拆文件不是整理癖，是**省上下文** |
| **代码既是可执行工具，也是文档**：要让 agent 清楚"该跑脚本还是该读它" | 脚本要写清用途，避免 agent 猜 |
| **安全考量**：引入外部 skill 需评估其能做什么 | skill 是权限面 |

## 三、工具设计（官方原则）

| 原则 | 官方要点 |
|:---|:---|
| **别只包 API** | 常见错误：把已有软件功能/接口原样包成工具。**agent 的"可供性（affordance）"与人不同**——它的约束是**上下文有限**，而计算机内存是廉价充裕的 |
| **工具不是越多越好** | 更多工具 ≠ 更好结果 |
| **命名空间** | 工具多了要分组，降低选择成本 |
| **返回有意义的上下文** | 返回值要**面向决策**，不是把原始数据倒出来 |
| **为 token 效率优化** | 返回值默认要小；截断/摘要/分页 |
| **用提示工程的思路写工具描述** | 工具描述就是给模型的提示词 |
| **原型 + 评测循环** | 先做原型，跑评测，再迭代（甚至让 Claude 帮忙优化自己的工具）|

## 四、与本库实践的对应（E3）

- 我们的 skill 库：`description` 规范、references/ 按主题拆分 —— 对应官方"渐进披露 + 为规模结构化"
- 我们的**门禁体系**（`kb_coverage_check.py` 等）——对应官方"**从评测出发**"：先有验收判据，再谈实现
- 我们的"一手不改写、逐节留 URL"——对应官方"**返回有意义的上下文**"（可回溯 > 全部倒出）

## 五、实操清单

- [ ] 我的每个 skill 的 **description 是否自包含触发条件**？（它常驻系统提示，是唯一选择依据）
- [ ] 我装了 200+ 个 skill——**常驻成本**算过吗？有没有该归档/合并的？
- [ ] `SKILL.md` 是否膨胀到该拆文件？互斥内容是否分开了？
- [ ] 我给的**工具返回值**默认多大？有没有截断策略？
- [ ] 工具是不是只把 API 包了一层？**换成 agent 视角**该怎么设计？
- [ ] 有没有"先评测后写"的循环，还是凭感觉加能力？
